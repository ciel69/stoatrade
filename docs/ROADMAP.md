# Роадмап: развивающийся мозг

Дата: 2026-11-02. Утверждён владельцем. Обсуждение и схема этапов: документ Claude Docs https://claude.ai/artifact/Rc9xoCCm9U4zWHMCrTAaZK; источник правды для разработки этот файл.

Цель: мозг, который с каждым торговым днём принимает решения измеримо лучше за счёт накопленного опыта. «Лучше» значит выше средний R после издержек и меньше нарушений правил, проверено статистически, а не на глаз. Старт работ по роадмапу после выпуска дашборда v2 (этап 0).

## Как ведётся разработка: spec-first

Каждый блок роадмапа (`R<этап>.<номер>`) до реализации превращается в спеку, и только потом в код.

1. Блок берётся в работу: создаётся спека по навыку `spec-first` в `.opencode/specs/R<этап>.<номер>-<slug>/` (`requirements.md`, `design.md`, `tasks.md`, формат навыка `kiro-specs`).
2. На этапе спеки блок разбирается детально: сценарии отказа, крайние случаи, контракты данных, влияние на слои (`tests/test_layering.py`), статистические критерии, вопросы владельцу. Формулировки этого файла — отправная точка, а не готовое ТЗ: спека может уточнить, разбить или пересмотреть блок.
3. Спека проходит независимое ревью и утверждается владельцем. Без утверждённой спеки код блока не пишется.
4. Реализация идёт по `tasks.md` спеки (субагентам по ТЗ, приёмка главным агентом), затем полный `./tb test`.
5. После приёмки в таблице статуса ниже ставится ссылка на спеку и статус; сделанное отражается в профильных документах (`ARCHITECTURE.md`, `BRAIN.md` и т. д.).

Статусы блока: `—` не начат · `спека` спека пишется · `утв.` спека утверждена · `в работе` · `реализовано в ветке` (код и тесты готовы, ждёт слияния и проверки на живых данных) · `готов` · `отложен`.

## Принципы

- Веса LLM не меняются: развивается система вокруг модели. Три слоя памяти: эпизодическая (случаи `tb.case/1`), смысловая (уроки и плейбук), процедурная (правила, пороги, веса признаков, промпты; новая версия вводится автоматически после проверки данными, см. «Самообучение без ручного одобрения»).
- Модель предлагает, код проверяет данными. Владелец не судит о трейдинге (уроки, сетапы, промпты): платформа автоматизирует трейдерскую работу целиком. Владелец решает только про риск и деньги: уровень риска, лимиты, плечо, размер, допуск к live, ключи.
- Нет вывода без статистики: n < 30 помечается, поправка на множественные сравнения, walk-forward без подглядывания в будущее.
- Дешёвые метки важнее дорогих решений: детерминированные политики и исходы сигналов дают объём, LLM даёт суждение поверх них.
- Каждое изменение мозга — гипотеза с версией, заранее записанным критерием и откатом.

## Самообучение без ручного одобрения

Владелец не обладает трейдерской экспертизой и не подтверждает уроки (решение 2026-11-02). Поэтому доказательство корректности даёт не человек, а данные вне выборки, а безопасность держится на асимметрии полномочий и автоматическом откате.

Путь знания до правила, полностью кодом:

1. **Кандидат.** Ревью дня (LLM) или поиск отклонений (код) предлагает урок `cond + claim` из словаря.
2. **Гипотеза.** Код проверяет его на истории (walk-forward, Бонферрони) и создаёт урок `hyp`.
3. **Подтверждение.** Урок становится `confirmed` по порогам: n ≥ 30, ≥ 5 дней, разные режимы рынка, эффект за пределами поправки. Новые данные опровергают его так же автоматически (`rejected`), уроки стареют и истекают.
4. **Теневое испытание.** Подтверждённый урок превращается в вариант правила (фильтр входа, требование подтверждения, понижение `size_mult`, правило выхода) и идёт тенью параллельно текущей версии на тех же сигналах, без влияния на решения.
5. **Продвижение.** Вариант становится частью плейбука новой версии `rules_ver`, если на заранее записанном n он лучше текущей версии по R после издержек и не хуже по числу сделок и нарушениям. Иначе отклоняется.
6. **Сторож отката.** После продвижения код сравнивает новую версию с прежней (прежняя продолжает идти тенью). Ухудшение за порогом — автоматический откат и запись причины.

Асимметрия полномочий, защищает без экспертизы владельца:

| Код может сам | Код не может никогда |
|---|---|
| ужесточать: пропускать сетапы и условия, требовать подтверждения, снижать `size_mult` ниже 1, раньше выходить, сужать окна торговли | ослаблять: повышать размер, плечо, лимиты, уровень риска, `size_mult` выше 1, ослаблять стоп |
| менять промпты ролей, веса признаков памяти, плейбук — через тень и продвижение | включать live, менять ключи, переводить средства |
| откатывать любую свою версию | обходить guard, Gate, KILL |

Роль владельца: читать страницу «Учится ли мозг» с простым вердиктом, выбирать уровень риска и давать команду на live. Кнопки «подтвердить / отклонить» остаются только как аварийное вмешательство, без них система работает полностью.

## Правила решений

1. Изменение мозга (плейбук, промпт, модель, веса памяти) вводится новой версией; критерий успеха записывается кодом до старта и не меняется по ходу.
2. Версия остаётся, если на n ≥ 100 она не хуже прежней по R и нарушениям; хуже — автоматический откат.
3. Урок становится правилом плейбука автоматически через тень и продвижение, но только если правило ужесточающее. Лимиты guard, размер, плечо и уровень риска код не меняет никогда.
4. Результаты paper в новостных окнах на live не переносятся.

| Режим рынка сменился | фильтры по возрасту и `rules_ver`, режим в признаках, срок годности уроков |
| Память «замораживает» торговлю | число сделок и упущенный R на странице «Учится ли мозг» |
| Локальная модель не успевает за потоком сигналов или слаба в суждениях | метки без LLM, метрики нагрузки R0.4, сравнение с облачными моделями R5.1 |
| Код подтверждает ложный урок без участия человека | пороги `confirmed`, теневое испытание вне выборки до продвижения, сторож отката, только ужесточающие правила |
| Ужесточения копятся и «замораживают» торговлю | продвижение требует не худшего числа сделок и упущенного R; ужесточение тоже проходит тень и откат |
| Подгонка под заранее известный результат | критерий записывается до испытания, тень на будущих сигналах, а не на истории |
| Отравление памяти текстом | только enum и числа, санитайзинг, пишут код, ревьюер и владелец |
