# План: новый фронт дашборда и переход с опросов на сокеты

Статус: план, код не начат (ветка `feat/frontend-vue` от `main`, 2026-10-30). Создан 2026-10-29 по запросу владельца. Решения, помеченные «РЕШИТЬ», принимает владелец до старта соответствующего этапа.

## 0. Решения владельца (2026-10-30)

1. **Фреймворк: Vue 3** (Vite, TypeScript, Pinia; SPA без SSR). Вопрос раздела 2 закрыт.
2. **Дизайн переделываем** с помощью навыка `impeccable`: пересмотреть удобство и состав главной страницы. Концепция «мозга» остаётся: на главной видно, что мозг работает, его результаты и «мысли» (последние решения и пояснения `brain_why`, события, на которые он реагирует) и **какая модель сейчас активна** (профиль, провайдер, ошибки и очередь).
3. **Транспорт: только WebSocket.** Старый подход с опросом (`setInterval`, long polling) в новом фронте не переносится. Это отменяет «запасной возврат к опросу» из раздела 4 (правило 2): при потере сокета интерфейс показывает «нет связи», переподключается сам и после восстановления получает снимок. Команды управления остаются POST с CSRF и nonce (раздел 3).
4. **Архитектура фронта: FSD (Feature-Sliced Design).** Слои `app` > `pages` > `widgets` > `features` > `entities` > `shared`, импорт только вниз, публичный API слайса через `index.ts`. Правило импортов проверять линтером (`eslint-plugin-boundaries` или `@feature-sliced/eslint-config`).
5. **Пакет общих компонентов** (`shared/ui`): небольшой набор кирпичиков, из которых собирается весь дашборд (карточка, плитка метрики, чип, бейдж состояния, таблица, сегмент-переключатель, модалка, подсказка, полоса прогресса, график-обёртка, пустое состояние). Токены темы (цвет, отступы, типографика, тёмная и светлая) живут в `shared/ui/tokens`.
6. **Новый дашборд на отдельном порту** (старый на 8766 не трогаем; новый поднимается одним сервисом рядом), владельцу сообщается порт при первом запуске, чтобы он смотрел результат по ходу работы.
7. **Работа поэтапная:** по одному этапу, после каждого показ результата и вопросы владельцу. Не весь дашборд сразу.

8. **Анимации:** все анимации проекта проектируются и пишутся через навык `animate` (решение: нужна ли анимация, что и каким свойством анимируем, кривая и длительность, прерывание, выход, `prefers-reduced-motion`). Правила движения фиксируются в `shared/ui/tokens` (длительности, кривые) и в `shared/ui/motion` (общие переходы), чтобы компоненты не придумывали своё.

Ответы на вопросы этапа 0 (2026-10-30):
- **WebSocket-сервер:** библиотека `websockets` (asyncio). Это первая внешняя Python-зависимость проекта: фиксируется в `requirements.txt`, ставится `pip install -r requirements.txt`.
- **Сборка:** `dist/` в репозиторий НЕ коммитим, фронт собирается при установке (`npm ci && npm run build` в `frontend/`; нужен Node.js 20+). Без сборки новый дашборд показывает страницу-заглушку с инструкцией.
- **«Мысли» мозга:** решения и пояснения (журнал решений `brain_decision` и `brain_why`, коды отказов, пропуски входа, события, на которые он отреагировал). Сырое рассуждение модели не хранится и не показывается.
- **Этап A (первый результат на новом порту):** оболочка + живая панель «Мозг» (активная модель, статус, последние решения).

Что ещё не решено, см. разделы 2.1, 3 и 8.

## 1. Зачем

Что не так сейчас (проверено по коду `src/tb/dash/`):

- **Постоянные опросы.** `app.js` запрашивает `/api/state` каждые 4 с (`POLL_MS`), `v-control.js` опрашивает `/api/ctl/status` и `/api/ctl/session` раз в секунду, результат команды `/api/ctl/result` каждые 0,7 с, отдельные таймеры у вкладок «День» и «Уведомления», `/api/brain/watch`. Они работают и когда данные не менялись.
- **Фронт без реактивности.** 22 файла на чистом JS с глобальными переменными (`CTL`, `ui`, `S`) и ручной перерисовкой. Перерисовку пропускают по «подписи» (`xcSig`, `_stFlowSig`). Забытое поле в подписи даёт баг вида «кнопка осталась отключённой, пока не обновишь страницу» (так было с модалкой смены риска, исправлено точечно 2026-10-29). Подобные баги будут повторяться.
- **Нет типов и тестов фронта.** Есть только Python-тесты, которые читают исходники JS как текст.

Цели:

1. Реактивный интерфейс на современном фреймворке: состояние в одном месте, перерисовка делается самим фреймворком.
2. Сервер отправляет данные при изменении (сокет), а в простое запросов нет.
3. Сохранить все гарантии безопасности текущего дашборда (раздел 5).

## 2. Решение по фреймворку (РЕШЕНО владельцем 2026-10-30: Vue 3)

Выбрано: **Vue 3 + Vite + TypeScript + Pinia**, режим SPA без SSR. Таблица ниже оставлена как обоснование.

| Вариант | За | Против |
|---|---|---|
| **Vue 3** (рекомендую) | Самая простая реактивность из трёх: `ref`/`computed` убирают класс ошибок «забыли перерисовать». Маленький порог входа. Компоненты на SFC близки к текущей верстке. Есть опыт в соседних проектах владельца (Nuxt) | Меньше готовых «финансовых» UI-наборов, чем у React |
| React | Огромная экосистема, много готовых графиков и таблиц | Ручное управление зависимостями эффектов и мемоизацией; вернётся часть сегодняшних проблем со «свежестью» |
| Angular | Строгая структура, RxJS хорошо ложится на потоки сокета | Тяжёлый для панели на одного пользователя; много шаблонного кода |

Nuxt не нужен: страница отдаётся локальным Python-сервером, SSR и серверный роутинг ни к чему.

Графики: оставить текущий `charts.js` на первом этапе (обернуть в компонент), потом при необходимости заменить на ECharts или uPlot.

### 2.1 Структура по FSD (`frontend/src/`)

```
app/        инициализация: роутер, Pinia, провайдеры, глобальные стили, подключение сокета
pages/      страницы-экраны (главная, сделки, планы, мозг, рынок, система ...): только сборка виджетов
widgets/    крупные самостоятельные блоки страницы (панель мозга, позиции, запас до лимитов, лента событий)
features/   действия пользователя с ценностью (войти по токену, сменить риск, начать/остановить день, подтвердить аварийную остановку)
entities/   бизнес-сущности и их отображение (позиция, план, сделка, модель, решение мозга, идея): типы, хранилище темы, мелкие компоненты
shared/     ui (пак общих компонентов), api (клиент сокета и POST), lib (форматтеры), config, tokens
```

Правила: слой импортирует только нижележащие; слайсы одного слоя не импортируют друг друга; публичный интерфейс слайса только через `index.ts`; данные темы сокета принадлежат `entities/<сущность>`, а не странице.

### 2.2 Главная страница и «мозг» (черновик, уточняется в этапе дизайна)

- Блок «Мозг» на видном месте: статус (работает, думает, ждёт, только защита), **активная модель** (профиль и провайдер, запасные, доля ошибок), очередь заданий, последние решения и их «мысли» (`brain_decision` и `brain_why`: что решил, почему, по какой монете), расход за сутки.
- Рядом то, что нужно для решения прямо сейчас: открытые позиции с защитой стопа, запас до лимитов, ближайшие события, состояние платформы.
- Остальное (рынок, идеи, эксперименты, настройки) уходит на отдельные страницы.
- Источники «мыслей»: журнал решений (`state/decisions.jsonl`, записи `brain_decision` с монетой и сигналом, `brain_why` постфактум после вызова инструмента) и события шины. Сырое рассуждение модели (`reasoning`) сейчас нигде не хранится; показывать ли его, решает владелец (см. вопросы этапа 0).

## 3. Решение по транспорту (РЕШИТЬ)

Требование владельца: вместо опросов использовать сокеты.

- **WebSocket** для потока «сервер -> клиент» (состояние, рынок, горячие монеты, идеи, сделки, статус управления, ход выполнения команды).
- **Команды остаются обычными POST** (`/api/ctl/challenge`, `/api/ctl/command`) с CSRF и nonce, как сейчас. Сокет только читает. Так не нужно переносить и заново проверять защиту опасных действий.
- Если на этапе 1 окажется, что WebSocket на стандартной библиотеке слишком хрупок, запасной вариант: **SSE** (`text/event-stream`) поверх того же `ThreadingHTTPServer`. Для односторонней отправки SSE достаточно, а переподключение встроено в браузер. Выбор фиксируем после прототипа.

Реализация на сервере (РЕШИТЬ):

- (a) своя минимальная реализация RFC 6455 на `http.server`/`socketserver` (проект сейчас без внешних Python-зависимостей; ~200 строк: рукопожатие, ping/pong, закрытие);
- (b) библиотека `websockets` (asyncio) отдельным потоком рядом с текущим сервером: надёжнее, но первая внешняя зависимость.
Рекомендация: начать с (a) в прототипе; если упрёмся в качество, перейти на (b).

Слушать только `127.0.0.1`, проверять `Origin` и `Host`, использовать ту же cookie-сессию и CSRF-токен, что и REST.

## 4. Протокол и источник изменений

Сообщение: `{"topic": "...", "seq": N, "ts": ..., "data": {...}}`.

Темы: `state` (сводка), `market`, `hot`, `ideas`, `trades`, `health`, `ctl` (статус платформы, сессия, аудит), `day` (ход старта и остановки), `brain` (решения мозга), `notify`, `exec` (результат команды по `id`).

Правила:

1. При подключении клиент получает **снимок** каждой подписанной темы (тот же JSON, что отдают текущие GET-эндпоинты), потом **изменения**. Клиент хранит последний `seq` и после обрыва запрашивает пропущенное или полный снимок.
2. Heartbeat раз в 15–20 с; клиент переподключается с нарастающей паузой и показывает индикатор «нет связи в реальном времени». **Возврата к опросу нет** (решение владельца 2026-10-30): после восстановления сокета приходит снимок тем.
3. Сервер отправляет тему, только когда её содержимое изменилось (хеш или `seq`), а не по таймеру на клиента.
4. Источник изменений на сервере: **один** общий цикл (не по циклу на клиента), который раз в ~1 с проверяет `mtime` и размер файлов (`runtime/*.json`, `state/*.jsonl`, `state/control/*`) и использует `seq` шины `core/bus`; пересобирает только затронутые темы через существующую `model.py`/`model2.py` (с их кэшем) и рассылает подписчикам. Это заменяет N браузеров × M опросов на один внутренний цикл. Позже можно заменить опрос файлов событиями от писателей.
5. Белые списки полей из `model2._BRIEF_ALLOW` и др. сохраняются: на клиент уходит то же, что отдают текущие GET.

## 5. Что нельзя потерять

- Вход по токену управления, сессия, CSRF, `nonce` с паузой и сроком, привязка команды к сессии и аргументам.
- Тексты третьих лиц (новости, названия) вставляются как текст, а не как HTML. В Vue использовать только `{{ }}`/`v-text`, **не** `v-html`.
- Слушаем только `127.0.0.1`.
- Сводки с белыми списками, никаких ключей и секретов в сообщениях.
- Подтверждение смены риска: список последствий + одна кнопка (сделано 2026-10-29), без набора текста. Поведение переносим как есть.

## 6. Этапы

Порядок уточнён 2026-10-30: работаем по одному этапу, после каждого владелец смотрит результат на **новом порту** (старый дашборд 8766 не меняется). Новый сервер поднимается отдельным сервисом уже с этапа 1 и показывает всё, что готово.

**Этап A. Каркас и живая связь (первый видимый результат).** Ветка `feat/frontend-vue`.
- Каталог `frontend/` (Vite + Vue 3 + TS + Pinia, структура FSD из 2.1, линтер границ слоёв).
- Сервер нового дашборда на отдельном порту (рядом с `./tb dash`, тот же `model.py` и белые списки): раздаёт собранный `dist/`, держит WebSocket, тема `state`/`brain`.
- `shared/ui/tokens` и 3–4 первых компонента (карточка, плитка, чип, индикатор связи), страница-оболочка с индикатором «связь есть» и живой панелью «Мозг» (активная модель, последние решения).
- Результат: открыть новый порт и увидеть живую панель мозга; в простое нет повторяющихся запросов.

**Этап B. Дизайн и главная.** Навык `impeccable`: сначала решение, что показывать на главной (брифинг и вопросы владельцу), затем дизайн-токены и макет, затем реализация виджетов главной.

**Этапы C… Перенос остальных экранов по одному** (порядок в этапе 3 ниже), каждый со своим набором общих компонентов, тестами и показом владельцу.

Детальный старый план этапов ниже сохранён как справка.

**Этап 0. Подготовка (1–2 дня).**
- Инвентаризация вкладок, эндпоинтов, полей, таймеров (раздел 1 — основа).
- Описать контракт данных каждой темы (JSON Schema или TypeScript-типы) и добавить Python-тесты контракта.
- Заморозить новые функции в старом UI, кроме исправлений.

**Этап 1. Push-слой на бэкенде (3–5 дней), старый фронт работает.**
- Общий цикл изменений, сервер сокета (или SSE), подписки по темам, снимок + изменения, heartbeat.
- Тесты: подключение, снимок, изменение файла -> одно сообщение, обрыв и восстановление, проверка `Origin`, неавторизованный клиент.
- Метрика до и после: число запросов в минуту в простое. Цель: 0 повторяющихся GET, кроме heartbeat.

**Этап 2. Каркас нового фронта (2–3 дня).**
- Vite + Vue 3 + TS + Pinia + Vue Router; сборка в `dist/`, раздача из Python (`static/` заменяется собранным каталогом); dev-режим с прокси.
- Дизайн-токены и тёмная/светлая тема из `app.css`.
- Клиент сокета: хранилища по темам, переподключение, индикатор связи.
- Базовая оболочка: шапка, чипы платформы, аварийная кнопка, вкладки.

**Этап 3. Перенос экранов по одному (≈2–3 недели).** За флагом `/?ui=new`; старый UI остаётся, пока экран не достигнет паритета.
Порядок: Обзор -> Управление (модалки, смена риска, старт дня) -> Решения -> Планы -> Сделки -> Идеи -> Рынок -> Досье -> День -> Уведомления -> Интел -> Эксперименты -> Настройки.
Для каждого экрана: компонент, тип данных, тест на мок-снимке, проверка в браузере.

**Этап 4. Переключение (2–3 дня).**
- Новый UI по умолчанию, старый за `/?ui=old` на одну неделю, затем удалить `static/*.js`, таймеры и лишние GET.
- Обновить `docs/CONTROL.md`, `docs/ARCHITECTURE.md`, `docs/RUNBOOK.md` (запуск, сборка, порт).

**Этап 5. Тесты и качество (идёт параллельно).**
- Модульные: Vitest (хранилища, форматирование, компоненты).
- Сквозные: Playwright на ключевых сценариях: вход по токену, старт дня, смена риска (повышение и понижение), смена вкладок и возврат (регрессия «кнопка не работает без F5»), обрыв сокета.
- Доступность: фокус в модалках, `Esc`, клавиатура, контраст.

## 7. Критерии готовности

1. В простое дашборд не делает периодических запросов, кроме heartbeat сокета.
2. Задержка от изменения файла до экрана меньше 2 с.
3. Паритет функций со старым UI по списку этапа 3; смена риска, старт и остановка дня проходят сквозные тесты.
4. После обрыва сети интерфейс сам восстанавливается и показывает актуальные данные без F5.
5. `./tb dash` по-прежнему запускается одной командой.

## 8. Риски и открытые вопросы

- **Node.js для сборки** (РЕШИТЬ): сейчас проект запускается без Node. Варианты: хранить собранный `dist/` в репозитории (запуск без Node, сборка только при разработке) или собирать при установке. Рекомендация: коммитить `dist/`.
- **Первая внешняя зависимость** на Python (если выберем `websockets`) и появление `package.json` с десятками пакетов: нужен регламент обновлений и аудит зависимостей.
- **Нагрузка на `ThreadingHTTPServer`**: долгоживущие соединения сокета занимают потоки; для одного пользователя это терпимо, но стоит ограничить число клиентов (например, 5).
- **Сроки**: перенос всех экранов самый объёмный этап; параллельно потребуется сопровождать старый UI.
- **Windows**: проверять сокет и сборку на Windows (основная среда владельца) и macOS.

## 9. Первые шаги, когда решите стартовать

1. Выбрать фреймворк (раздел 2) и транспорт (раздел 3).
2. Выбрать, коммитим ли `dist/`.
3. Начать с этапа 0 и прототипа этапа 1 (один топик `state` по сокету рядом со старым `/api/state`), чтобы измерить выигрыш до переноса экранов.
