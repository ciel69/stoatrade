# Уровни риска (WP16)

Риск считается от капитала и настраивается одним переключателем: уровень 1-5. `config/risk_profile.json` остаётся БАЗОЙ; `config/risk_levels.json` задаёт пресеты поверх неё и жёсткие потолки. Уровень 3 «Базовый» воспроизводит прежние значения: `effective` возвращает базу без изменений, вывод `./tb guard` и `./tb bybit trade open --dry-run` идентичен прежнему (тест эквивалентности `tests/test_risklevels_guard.py`: 267 сценариев, золотой файл `tests/fixtures_wp16/guard_golden.json` записан со СТАРОГО guard).

Уровень 3 = прежнее поведение. Уровни 4-5 подтверждены владельцем 2026-11-01 (эксперимент: риск осознан; размер сделки, маржа и квоты выживания растут с уровнем; потолки подняты). Уровни 1-2 остаются ПРЕДЛОЖЕННЫМИ (спецификация `spec_v2/07_control_lifecycle_news_roles.md` п. 4.2); загрузчик показывает предупреждение о каждом непроверенном выбранном уровне. Подтверждение = номер в `confirmed_levels` файла `risk_levels.json`.

Пояснения. Плечо = `max_leverage` базы и типа сессии x множитель (не выше базы). «+ к min RR» прибавляется к `min_rr` базы и типа сессии (на уровне 3 ноль, значения базы не трогаются). `total_open_risk` вводится в guard только когда строже неявного (позиции x риск сделки): на уровнях 1-3 это не меняет поведения. Размер сделки считается guard: `equity x риск/сделка x (0.5 + 0.5 score) x множитель просадки x множитель по результатам`, дальше потолки маржи (`margin_per_trade_frac` уровня, иначе базы), плеча и комиссий; планы `entry_scout` на уровнях 4-5 идут со `score = 1.0` (полный бюджет риска, `entryplan.FULL_SIZE_LEVEL`). Квоты выживания (`min_trades_day`, `min_net_day_frac`) попадают в досье мозга `economics` (`min_trades_day/trades_left`, `min_net_day_usdt/net_left_usdt`) и в системный промпт (SURVIVAL): они заставляют искать входы и прибыль, но не ослабляют стоп, RR, паузы и лимиты. Лимиты агента `api` в `agents.json` (`max_risk_pct` 8, `max_risk_usdt` 4) подняты до потолков, чтобы не резать уровни 4-5.

## Итоговые лимиты = минимум
Для каждого лимита действует МИНИМУМ из: пресета уровня, потолка, `agents.json limits` (`max_risk_pct`, `max_risk_usdt`, `max_size_mult`, `allow_add`) и `exec_limits.json` (`entry.no_confirm_max_size_mult`, `pyramid.*`). `./tb risk level show` печатает итог и расхождения («агент chat: limits.max_risk_pct=6.0 выше уровня 3»), `exec_cfg.warnings()` предупреждает, когда `exec_limits` расходится с уровнем. Лестница просадки (`drawdown_ladder`, `drawdown_halt`) НЕ отключается и применяется ПОСЛЕ уровня.

## Выбор уровня и подпись
- Файла нет -> `default_level` (3). Файл есть, но ключа подписи нет, подпись неверна, мусор или неизвестный уровень -> **уровень 1** (безопасный) и предупреждение.
- Файл `state/control/risk_level.json`: `{"level":3,"since":"…Z","by":"owner|auto","history":[{"ts","from","to","by","why"}],"mac":"<hex>"}`, `mac = HMAC-SHA256(hmac_key, canonical_json(тело без mac))`, canonical = `json.dumps(sort_keys=True, separators=(",",":"), ensure_ascii=False)`. Ключ `hmac_key` (hex, >= 32 символов) лежит в `<TB_KEYS_DIR | ~/.config/traider-bot>/control.json`, читает его одна функция `risklevels._read_key()`.
- Ключ создаёт владелец командой `./tb risk init-key` в Terminal (нужен TTY): файл с правами 0600 только если его ещё нет; значение не печатается; существующий файл не читается и не затирается (на Windows проверьте ACL через `icacls`). Агент ключ не создаёт и не читает.
- Смена: `./tb risk level set N --confirm "УРОВЕНЬ РИСКА N <имя>" [--accept ID ...] [--ack "я принимаю риск"]` (нужен TTY). Без `--confirm` команда ничего не меняет и печатает фразу и предупреждения. Повышение до 4-5: каждое обязательное предупреждение принимается отдельно (`W_UNCONFIRMED`, `W_TRADE_LOSS`, `W_DAY_LOSS`, `W_PYRAMID`, `W_CARRY`, `W_NO_CONFIRM`) и фраза «я принимаю риск». Кулдаун между повышениями `cooldown_min` (60). Понижение: только фраза. Любая смена пишется в аудит `state/control/risk_audit.jsonl` и событие шины `risk_level_changed` (`from`, `to`, `by`, `why`). Смена применяется к НОВЫМ входам, действующие планы сохраняют риск `risk0`.
- Агент и шлюз уровень менять не могут: в каталоге шлюза нет инструмента, файл подписан, пакеты gateway/mcp/brain/llm не импортируют `tb.control` и не зовут `set_level` (тесты `NoAgentPath`). Права для чата (предлагается владельцу в `PERMISSIONS.md`): `deny` на `Bash(./tb risk level set *)`, `Bash(./tb risk init-key)`; `allow` на `./tb risk level show|list|check`.

## Авто-понижение
`./tb risk level check [--apply]` и `risklevels.auto_downgrade` (его вызывает `ctl`): уровень падает на ступень, если просадка достигла ступени лестницы (код `dd_<порог>_<дата>`, глубже ступень = новая причина) или результат за день <= -70% дневного лимита (`daily_loss_<дата>`). Одна причина понижает один раз, ниже 1 не идёт, повысить автоматически нельзя, после выхода из просадки уровень не возвращается (только владелец). Пишет подписанный файл, поэтому нужен ключ.

## Запросы политик (для WP5, WP9, WP14)
`risklevels.carry_policy(root)`, `pyramid_policy(root, exec_limits, agent_limits)`, `no_confirm_policy(root, exec_limits)`, `size_mult_cap(root, agent_limits)`, `setup_allowed(setup, root) -> (ok, "E_SETUP_AGGR")`, `limits_summary(root, agent_limits, equity)`. Скальп не переносится ни на каком уровне. `guard.evaluate` принимает необязательные `a.agent_limits` и `a.setup`; без них поведение прежнее.

Подробности расхождений и принятых решений: `docs/spec_v2/WP16_guard_notes.md`.
