# Бриф: десктопное приложение (Tauri + Python sidecar)

Статус: бриф, код не начат. Создан 2026-10-31 по запросу владельца. Старт после завершения нового фронта (`docs/FRONTEND_PLAN.md`, ветка `feat/frontend-vue`).
Решения, помеченные «РЕШИТЬ», принимает владелец до старта соответствующего этапа (раздел 11).

## 1. Цель и рамки

Цель: платформа ставится и запускается как обычное приложение Windows и macOS: установщик, ярлык, окно с новым дашбордом, значок в трее, автообновление.
Терминал, Python и Node.js у пользователя не нужны.

Входит:
- окно с новым фронтом (Vue, `frontend/dist`) и запуск платформы (супервизор и все сервисы) из приложения;
- работа в фоне: закрытие окна не останавливает торговлю, управление из трея;
- ключи в системном хранилище (Windows Credential Manager, macOS Keychain);
- установщик, подпись, автообновление, сборка в CI под обе ОС.

Не входит:
- изменение торговой логики, лимитов, guard и мозга (приложение только упаковывает то, что есть);
- встраивание локальной модели (gpt-oss через Ollama остаётся отдельной программой, раздел 9);
- мобильная версия и облачный режим.

## 2. Решение: Tauri 2 + Python sidecar

Оболочка на Tauri 2 (Rust, системный WebView: WebView2 на Windows, WKWebView на macOS). Python-платформа собирается PyInstaller'ом в отдельный исполняемый файл
`tb-core` и запускается оболочкой как sidecar. Фронт грузится с локального сервера `dash2` (127.0.0.1), как сейчас в браузере.

Почему так:
- установщик 30-60 МБ без Python (Electron тянет Chromium, 150+ МБ и заметно больше памяти);
- в Tauri из коробки трей, одно-экземплярность, автообновление с подписью, уведомления ОС, автозапуск;
- Python-код остаётся как есть: оболочка только запускает, останавливает и показывает.

Отклонены: Electron (вес, память), pywebview (слабый трей, установщики и обновления пришлось бы собирать вручную).

| Команда сервиса | `services.service_cmd` (`src/tb/platform/services.py:296`) | Все сервисы запускаются как `sys.executable -m tb.<модуль>`: в собранном exe так не работает (5.1) |

| Ключи | `launcher.key_dirs`: `~/.config/traider-bot/`, на Windows ещё `%APPDATA%\traider-bot\`, файлы `bybit_*.env` и ключи провайдеров LLM | Ключ исполнителя грузится внутри его процесса, не супервизора |

| Первый запуск | `./tb setup` / `tb.cmd setup`: проверка среды, установка Python и `websockets`, LLM, запуск (`src/tb/setup_env.py`, `scripts/bootstrap.*`) | Для приложения не нужен: Python и зависимости внутри `tb-core`; проверки среды (порт, часы, доступ к Bybit) можно переиспользовать |
| Остановка | супервизор ловит SIGINT/SIGTERM/SIGBREAK, порядок `stop_order`: исполнители последними | Оболочка должна останавливать мягко, а не убивать процессы (5.5) |
| Зависимости Python | `requirements.txt`: `websockets>=13` | Собирается в `tb-core` |
| Локальная модель | `config/providers.json` провайдер `local`: `http://127.0.0.1:11434/v1` (Ollama) | Отдельная программа (раздел 9) |

## 4. Архитектура приложения

```
Stoa.app / .exe  (Tauri, Rust)
 ├─ окно WebView  ──http/ws──>  127.0.0.1:<порт dash2>
 ├─ трей: открыть, состояние, остановить день, KILL, выход
 └─ sidecar: tb-core supervise   (супервизор)
      ├─ tb-core svc exec | scan | feed | context | intel | sync | dispatch | ctl | brain | dash2
      └─ данные: <каталог данных пользователя>/{config,state,runtime,data,logs}
```

- Один исполняемый `tb-core` (PyInstaller, режим onedir) обслуживает и супервизор, и каждый сервис: первый аргумент выбирает роль (5.1).
- Каталог данных пользователя: Windows `%APPDATA%\Stoa\`, macOS `~/Library/Application Support/Stoa/`. Туда при первом запуске
  копируются умолчания `config/` из ресурсов приложения; дальше это рабочая копия владельца.
- Ресурсы приложения только для чтения: `frontend/dist`, умолчания `config/`, промпты ролей `config/roles/`.
- Порт `dash2`: занят -> следующий свободный; оболочка узнаёт фактический порт из файла, который пишет `dash2` (например `runtime/dash2.json`).

Жизненный цикл:
1. Старт приложения: одно-экземплярность (второй запуск открывает окно первого). Если супервизор уже работает (запущен из терминала), приложение к нему подключается, а не стартует второй.
2. Иначе запуск `tb-core supervise --profile <последний профиль, по умолчанию paper>`, ожидание готовности `dash2` (проба HTTP), затем окно.
3. Закрытие окна: окно прячется, платформа работает, в трее значок состояния.
4. «Выход» из трея: подтверждение; при открытых позициях или live-дне отдельное предупреждение (позиции остаются под биржевыми стопами); затем мягкая остановка супервизора (как `./tb stop`), ожидание до таймаута, только потом принудительное завершение.
5. Live-профиль никогда не включается автоматически при старте приложения: только явным действием владельца, как сейчас (`up --profile trade --i-understand-live`).

## 5. Доработки Python-части (до оболочки)

### 5.1 Единая точка входа для собранного exe
`service_cmd` строит `[sys.executable, "-m", "tb...."]`. В собранном exe `sys.executable` указывает на сам `tb-core`, а `-m` не работает.
Нужно: модуль `tb/frozen_main.py` (точка входа PyInstaller) с диспетчером `tb-core svc <имя> [аргументы]` и `tb-core <команда launcher>`;
`service_cmd` при `getattr(sys, "frozen", False)` строит `[sys.executable, "svc", name, ...]`. В обычном режиме всё как сейчас.
Готово, когда `tb-core start` поднимает все сервисы по умолчанию и `tb-core status` зелёный на чистой машине без Python.

### 5.2 Дашборд как сервис супервизора
Сделано частично: новый дашборд уже сервис `dash` в наборе по умолчанию (порт 8765 из `config/platform.json` -> `svc.dash.port`). Осталось: запись фактического порта в `runtime/dash2.json` (порт занят -> следующий свободный) и heartbeat по файлу.

### 5.3 Разделить код, ресурсы и данные
`paths.root()` сейчас = папка проекта. Нужно: `paths.resources()` (только чтение: `frontend/dist`, умолчания конфигов, роли) и корень данных (`TB_ROOT`).
Первый запуск: копирование умолчаний в каталог данных; при обновлении приложения новые ключи умолчаний добавляются, правки владельца не перезаписываются.
Миграция с текущей установки из репозитория: команда «перенести данные» копирует `config/`, `state/`, `data/` в каталог данных (РЕШИТЬ: переносить или начинать с чистого).

### 5.4 Ключи в системном хранилище
`launcher` получает ещё один источник ключа: системное хранилище через пакет `keyring` (новая зависимость). Порядок: хранилище -> файлы `.env` (как сейчас).
Ввод ключа: окно приложения с полем ввода; значение уходит прямо в хранилище и никогда не отображается обратно, не пишется в логи и в `state/`.
Правило проекта сохраняется: ключи создаёт и вводит только владелец; агент их не читает.

### 5.5 Мягкая остановка из оболочки
Команда `tb-core stop --timeout N` (уже есть `./tb stop`): оболочка вызывает её и ждёт. На Windows проверить доставку SIGBREAK дочерним процессам sidecar
(процессы без консоли): при необходимости остановка через файл-флаг супервизора вместо сигнала.

### 5.6 Сборка фронта
Собранный `frontend/dist` лежит в репозитории (с 2026-11-02, чтобы запуск из клона не требовал Node.js). Для приложения CI всё равно собирает `npm ci && npm run build` заново и кладёт результат в ресурсы. Node.js у пользователя не нужен.

## 6. Оболочка Tauri

- Проект `desktop/` (Tauri 2): `src-tauri/` (Rust), конфиг `tauri.conf.json`, sidecar `tb-core` в `bundle.externalBin` (onedir: каталог ресурсов + запуск через shell-плагин).
- Окно грузит `http://127.0.0.1:<порт>` из `runtime/dash2.json`. Проверки Host и Origin в `dash2` уже есть: убедиться, что WebView шлёт ожидаемый Origin.
- Трей: «Открыть», состояние (зелёный/жёлтый/красный по `./tb status`), «Остановить день», «KILL (только защита позиций)», «Выход». KILL и остановка через те же команды ctl, что в дашборде.
- Уведомления ОС: сейчас их шлёт Python (`docs/NOTIFICATIONS.md`); в приложении оставить так или перевести на плагин уведомлений Tauri (РЕШИТЬ).
- Автозапуск при входе в систему: выключен по умолчанию, включается владельцем (РЕШИТЬ).
- Одно-экземплярность: плагин single-instance.

## 7. Безопасность и деньги

1. Приложение не меняет лимиты, уровень риска, guard и права: только запуск, остановка, показ.
2. Live не стартует сам: ни при запуске приложения, ни после обновления, ни после перезагрузки ОС.
3. Закрытие окна не равно остановке; выход с открытыми позициями только после явного подтверждения.
4. Обновление не ставится во время открытых live-позиций или активного live-дня: только после остановки дня.
5. Подпись: обновления проверяются подписью Tauri updater; установщики подписаны (раздел 8).
6. Сервер `dash2` слушает только 127.0.0.1, как сейчас; никаких внешних портов.
7. Ключи только в системном хранилище или в файлах владельца; в логах, `state/`, отчётах и сборке их нет (проверка в CI: поиск секретоподобных строк в артефакте).

## 8. Сборка и выпуск

- CI (GitHub Actions): матрица `windows-latest`, `macos-latest` (arm64 и x64 или universal, РЕШИТЬ).
  Шаги: сборка фронта -> PyInstaller `tb-core` (onedir) -> `./tb test` на собранном `tb-core` (дымовой запуск paper) -> `tauri build` -> подпись -> артефакты и манифест обновления.
- PyInstaller onedir, а не onefile: быстрый старт (onefile распаковывается при каждом запуске) и меньше ложных срабатываний антивирусов.
- Подпись Windows: сертификат Authenticode (OV или EV; без него SmartScreen предупреждает). macOS: Developer ID и нотаризация (аккаунт Apple Developer). Стоимость, РЕШИТЬ.
- Автообновление: Tauri updater, ключ подписи обновлений хранится в секретах CI, не в репозитории.
- Версия приложения = версия проекта; в окне «О программе» версия и хеш коммита.

## 9. Локальная модель

Модель в установщик не входит (гигабайты). Приложение проверяет доступность провайдера `local` (`http://127.0.0.1:11434/v1`) и показывает состояние:
«локальная модель недоступна: запустите Ollama» или подсказку переключить роли на облачного провайдера. Платные провайдеры работают через API, как сейчас.

## 11. Решения владельца (РЕШИТЬ до D1)

1. Название приложения и каталога данных: решено, «Stoa», каталог `Stoa` (репозиторий `stoatrade`).
2. Платформы и порядок: только Windows сначала, или Windows и macOS сразу; для macOS arm64, x64 или universal.
3. Подпись: покупать сертификаты сразу (стоимость в год) или первые версии без подписи только для себя.
4. Данные: переносить текущие `config/`, `state/`, `data/` из репозитория или начинать с чистой установки.
5. Ключи: только системное хранилище или хранилище плюс прежние `.env` файлы.
6. Автозапуск при входе в систему и автоматический старт paper-дня при запуске приложения.
7. Уведомления: оставить Python или перевести на Tauri.
8. Канал обновлений: автоматически или по кнопке.
9. Live в десктопе: разрешён с теми же подтверждениями, что в CLI, или на первых версиях только paper и testnet.

## 12. Риски

- Антивирусы на Windows считают неподписанные PyInstaller-сборки подозрительными: подпись и onedir снижают риск.
- Сигналы остановки в процессах без консоли на Windows ведут себя иначе, чем в терминале: проверить на D2, иметь запасной путь через файл-флаг.
- Две копии платформы (из терминала и из приложения) с одним каталогом данных: защищает существующий lock исполнителя, но приложение должно явно подключаться к уже запущенному супервизору.
- Обновление посреди торгового дня: запрещено правилом 7.4, проверка в коде оболочки.
- Рост размера `tb-core` из-за зависимостей: следить, не тянуть научные пакеты в рантайм (исследовательские скрипты не входят в сборку).
