# RUNBOOK: платформа v2 (WP11-B)

Платформа = супервизор + сервисы под ним. Запускается одной командой, живёт без чата и без агента Claude. Сервисы: `exec` (исполнитель), `scan` (сканер как сервис),
`dispatch` (диспетчер подписок), `ctl` (сервис управления, WP12: `docs/CONTROL.md`), `dash` (дашборд: с 2026-11-02 новый, Vue + WebSocket, порт 8765; живость не проверяется, `hb: none`; запускается как `./tb dash --port N`), `mcp` и `brain` (резерв: см. ниже). Код: `src/tb/platform/`, настройки: `config/platform.json`, `config/subscriptions.json`.

## Команды
Просто: `./tb start` (всё в фоне, профиль из `config/local/platform.json`, иначе paper; мозг входит в набор и стартует, если есть условия, иначе одна строка «мозг выключен: ...»), `./tb stop`, `./tb restart`, `./tb status`.
`start` не включает trade. Приостановленный (Ctrl+Z, состояние T) супервизор/сервис платформы `start|stop|restart|down` размораживают SIGCONT (только свои pid из `runtime/platform/*.pid` и `supervisor.lock`; KILL -9 не используется); не вышло: печатается ручная инструкция. Код: `src/tb/platform/quick.py`, `freeze.py`.
Расширенные параметры:
```
./tb up [--profile paper|testnet|trade] [--observe] [--services exec,scan,feed,context,intel,sync,dispatch,ctl,dash] [--detach] [--max-seconds N] [--dry-run]
./tb status [--json|--line]       сводка (код 0 платформа запущена, 1 нет); --line одна строка для статусной строки
./tb logs [platform|exec|scan|dispatch|dash] [-n 50] [-f]
./tb down [--timeout 45]          остановка всех сервисов (исполнитель последним)
./tb dispatch <check|once|queue ID [--ack N]|stats|log>
./tb up --print-launchd | --print-windows      напечатать файл автозапуска ОС (ничего не устанавливается)
```
По умолчанию профиль `paper` и сервисы `exec, scan, feed, context, intel, sync, dispatch, ctl, dash, labels, learnloop, brain` (brain отсеивается, если нет условий). `up` печатает профиль и список сервисов. Ctrl+C в окне `up` останавливает всё так же, как `down`.
Вторая копия на том же корне отказана блокировкой (`runtime/platform/supervisor.lock`, код 4). Корень можно задать `TB_ROOT` или `--root`.

## Запуск, статус, остановка
1. Рядом с терминалом: `./tb up` (окно занято; Ctrl+C останавливает) либо в фон: `./tb up --detach` (платформа живёт без терминала и без чата).
2. `./tb status`: цвет (зелёный, жёлтый, красный, выключена), таблица сервисов (состояние, pid, аптайм, heartbeat, перезапуски, последняя ошибка), исполнитель (жив, режим, позиции, hold, KILL),
   возраст шины и сканера, непрочитанное по очередям, ссылка на дашборд. То же в JSON: `./tb status --json`; в дашборде `/api/platform`; файл `runtime/platform/status.json` (блок сервисов).
3. `./tb down`. Если открыты позиции, будет напоминание: исполнитель остановлен, позиции держит биржевой стоп.

## Профили и безопасность
- `paper`: исполнитель на бумажном порту, ключи не нужны.
- `testnet`: ключ testnet грузит `tb.launcher` внутрь процесса исполнителя.
- `trade` (МАЙНЕТ, реальные деньги): только `./tb up --profile trade --i-understand-live` и только когда `state/KILL` отсутствует. Иначе отказ с кодом 2. Перед стартом печатается профиль и состав сервисов.
- Ключи Bybit и Anthropic есть ТОЛЬКО в процессе исполнителя (его launcher). Все остальные сервисы запускаются с окружением без `BYBIT_*`, `ANTHROPIC_*` и без прокси (тест `test_platform_supervisor`); у `labels` чистка шире (`DEEPSEEK_*`, `OPENAI_*`, `*_API_KEY`, `*_SECRET`, `*_TOKEN`).
- `--observe`: исполнитель только наблюдает, ордеров не отправляет.

## Автоперезапуск, heartbeat, деградации
- Упавший сервис перезапускается с паузой `base_s * factor^(n-1)` (2, 4, 8, ... до 60 с). После `max_tries` (5) сбоев подряд сервис помечается `failed`, в шину пишется событие `service_down`
  (приоритет wake, не чаще раза в час на сервис), статус красный. Сдавшийся сервис пробуется заново раз в `retry_after_giveup_s` (15 мин); коды выхода 2 и 4 в первые секунды (ошибка запуска, второй экземпляр) не перезапускаются.
- Сервис проработал дольше `stable_s` (120 с): счётчик сбоев обнуляется.
- Heartbeat: `exec` = `runtime/exec_health.json` (60 с), `scan` и `dispatch` пишут `runtime/platform/<сервис>.hb.json`. Живой процесс с устаревшим heartbeat после льготного срока убивается и перезапускается.
- Исполнитель упал при открытых позициях: красный статус и напоминание, что позиции защищены биржевым стопом, но не ведутся. Что делать: `./tb status`, `./tb logs exec`, при необходимости `./tb bybit read positions`,
  закрыть вручную; после починки `./tb up`.

## Если что-то не так
| Симптом в `./tb status` | Причина | Действие |
|---|---|---|
| сервис `failed`, код 4 (exec) | исполнитель уже запущен отдельно (`exec run` в другом окне) | остановить его (Ctrl+C) и `./tb up` |
| сервис `failed`, код 2 | неверный запуск (`mcp` без параметров) | `./tb logs <сервис>`, убрать из `--services` |
| `backoff` | идёт перезапуск | подождать; смотреть `./tb logs <сервис>` |
| сканер не обновляет hot.json | нет доступа к REST Bybit (прокси, блокировка) | `./tb bybit read scan` из терминала; платформа запускает сканер без прокси |
| «платформа не запущена» при живых процессах | супервизор убит жёстко | `./tb down` (зачистит сирот по pid-файлам), затем `./tb up` |
| `status.json не обновляется` | супервизор завис | `./tb down`, `./tb up` |
| красный: мозг в «только защите» | бюджет LLM исчерпан или профили недоступны (ключ, сеть, 5xx) | `./tb brain status`, `./tb llm usage`, `./tb llm check --live`; позиции ведёт исполнитель, вручную при необходимости `./tb exec halt --flatten` |

## Ночной прогон (observe)
`./tb up --profile paper --observe --detach` (или testnet). Утром: `./tb status`, `./tb events stats`, `./tb dispatch stats`, `./tb logs platform -n 100`. Остановка: `./tb down`.
Во время прогона чат не нужен: события копятся в шине и очередях подписчиков, API-мозг (если включён) получает задания.

## Автозапуск ОС (ставит владелец)
Платформа ничего не устанавливает сама. `./tb up --profile paper --print-launchd > ~/Library/LaunchAgents/com.traider-bot.platform.plist`, затем `launchctl load ~/Library/LaunchAgents/com.traider-bot.platform.plist`
(снять: `launchctl unload ...`). Плист перезапускает платформу при НЕнулевом выходе; `./tb down` завершает её кодом 0 и launchd её не поднимает.
Windows: `./tb up --print-windows` печатает PowerShell-скрипт с `Register-ScheduledTask` (старт при входе, повтор при сбое); сохранить в файл и один раз выполнить. Снять: `Unregister-ScheduledTask -TaskName TraiderBotPlatform`.
Профиль `trade` в автозапуск вносить осознанно: нужны флаги `--i-understand-live` в аргументах, KILL должен быть чист.

## Чек-лист перед live
1. `./tb test` зелёный; `./tb exec verify` без ошибок.
2. Был прогон `paper` и `testnet` с `--observe` не меньше суток без `service_down`.
3. `config/risk_profile.json`, `config/exec_limits.json` не менялись без указания владельца; `state/KILL` отсутствует осознанно (`./tb exec resume`).
4. Ключ `bybit_mainnet_trade.env` на месте (проверяет сам исполнитель; содержимое не печатать).
5. `./tb up --profile trade --i-understand-live --dry-run` показывает ожидаемые сервисы; в `config/subscriptions.json` только нужные подписчики.
6. Дашборд открыт, `./tb status` зелёный, `./tb dispatch stats` без замечаний.
7. Известен порядок остановки: `./tb exec halt --flatten` (аварийно), затем `./tb down`.

## config/platform.json
Недостающие ключи берутся из `tb.platform.services.DEFAULTS`. Разделы:
- `profile`, `services.<профиль>`: список сервисов по умолчанию.
- `supervisor`: `poll_s`, `status_s`, `stop_grace_s`, `exec_stop_grace_s`, `stable_s`, `restart{base_s,factor,max_s,max_tries}`, `retry_after_giveup_s`, `fatal_codes`, `fatal_within_s`, `down_event_repeat_s`, `log{max_bytes,keep}`.
- `svc.<сервис>`: `hb` (`exec`|`file`|`none`), `hb_stale_s`, `grace_s`, для `dash` (8765) `port`, для `mcp`/`brain` `module` и `args`.
- `scan`: пороги прежние (hotscan): `interval, top, min_turnover, max_spread_bps, max_lot, range_pct, surge_min, cooldown, wake_score, max_per_hour, idea_zone_pct, outcome_min`; `env` (рынок, по умолчанию mainnet:
  публичные данные), `publish_info` (тихие события тоже в шину как info), `dedup_s` (окна дедупликации по виду события).
- `dispatch`: `poll_s`, `retry_*`, `max_attempts` (webhook), `api{jobs_per_hour, critical_per_hour, coalesce_s, settle_s, max_seqs}`, `queue_keep`, `classes` (тип события -> класс приоритета).

## config/subscriptions.json (реестр подписчиков)
Поставляемый файл держит `api` выключенным. Личные настройки владельца лежат в `config/local/<имя>.json` (каталог в `.gitignore`): глубокое слияние поверх `config/<имя>.json`, списки с `id` (подписчики) сливаются по id, прочие значения заменяются; битый локальный файл игнорируется с предупреждением в stderr. Подключено для `subscriptions`, `intel` (`sources.<id>.verified`, `reader.enabled`), `platform`, `providers`, `brain`. Включить мозг: `./tb brain enable` (пишет `config/local/subscriptions.json` = `{"subscribers": [{"id": "api", "enabled": true}]}`) (диспетчер подхватывает на лету, остальные сервисы при перезапуске). Код: `src/tb/core/localcfg.py`.
```json
{"subscribers": [
  {"id": "chat", "enabled": true, "delivery": "queue", "filter": {"pri": "wake"}, "rate": {"max_per_hour": 120}},
  {"id": "api", "enabled": false, "delivery": "api_agent", "filter": {"pri": "wake", "max_class": 3}, "rate": {"jobs_per_hour": 12, "coalesce_s": 60}},
  {"id": "hook", "enabled": false, "delivery": "webhook", "url": "http://127.0.0.1:9099/events", "filter": {"pri": "wake"}},
  {"id": "cmd", "enabled": false, "delivery": "exec_cmd"}]}
```
`id`: `a-z0-9_-` до 20 символов. `delivery`: `queue` | `api_agent` | `webhook` (только localhost/127.0.0.1/[::1], иначе подписчик отвергается) | `exec_cmd` (не поддерживается: запись «unsupported» в журнале, команда не запускается).
`filter`: `types` (список или `["*"]`), `exclude_types`, `kinds` (виды `scanner_signal`), `pri` (`wake` = только wake), `max_class` (0..4), `syms`. `rate`: `max_per_hour`, `min_gap_s` (события класса 0 не режутся).
`start_at`: `end` (по умолчанию: новый подписчик не получает историю) или `begin`. Включить можно только `"enabled": true`.
Классы приоритета: 0 связь, kill, лимиты, ошибки, `service_down`; 1 исполнение; 2 вехи позиции; 3 сигналы сканера; 4 идеи (`idea_*`).

## Диспетчер: как агент забирает события
Диспетчер читает шину своим курсором на каждого подписчика (`state/dispatch/subs/<id>.cursor.json`), доставка at-least-once и идемпотентна по `seq`. Журнал: `state/dispatch/deliveries.jsonl`
(`./tb dispatch log`): ok, dup, coalesced, rate, cap, retry, failed, unsupported.
- `queue`: файл `state/dispatch/queues/<id>.jsonl`, записи `{"q","seq","ts","type","pri","cls","plan"?,"sym"?,"d"}`; забрать `./tb dispatch queue <id> [--after Q] [--limit N] [--wake-only]`, подтвердить `--ack Q`.
  Библиотека для MCP (WP11-A): `from tb.platform.dispatcher import Queue; q = Queue(root, "chat"); q.read(); q.ack(n); q.stats()`.
  Счётчик непрочитанного: `runtime/platform/unread.json` (`{"chat":{"unread","wake_unread","oldest_wake_age_s",...}}`), он же в `./tb status` и в `build_status()["unread"]`.
- `api_agent` (для API-мозга, WP11-C): задания `state/brain/jobs/J-*.json` со `status:"new"`. Поля: `id, sub, status, prio (лучший класс), key (plan:ID | sym:СИМВОЛ | type:ТИП), plan, sym, ts_first, ts_last, not_before,
  count, seqs, types, kinds, dropped_before`. Серия событий по одному плану/символу в окне `coalesce_s` сворачивается в одно задание (`count` растёт, приоритет повышается, критичное снимает `not_before`).
  Потолок: `jobs_per_hour` обычных и `critical_per_hour` критичных (класс 0) в час; сверх потолка события в задания не идут (счётчик `dropped_before` следующего задания). Мозг берёт только задания с `not_before <= now`,
  меняет `status` `new -> taken -> done` (запись файла целиком; диспетчер коалесцирует только в `new`). Тексты третьих лиц в заданиях невозможны: только поля событий шины.
- Чат Claude Code диспетчер НЕ будит: это невозможно. События лежат в очереди `chat`, счётчик виден в `get_status`/`./tb status --line`; чат читает их при следующем обращении (`get_events`, `wait_events`).

## Сканер как сервис
`python -m tb.platform.scansvc run` (запускает супервизор) гоняет тот же `hotscan` (пороги из `config/platform.json`, раздел `scan`) и публикует в шину `scanner_signal` (kind: `range_5m`, `turnover_surge`, `hot_enter`,
`idea_near`, `idea_level`, `idea_invalidated`, `idea_tp`, `idea_expired`, `idea_stale`) с белым списком полей и дедупликацией (ревизия идей: пороги `config/idea_stale.json`, см. docs/BRAIN.md). Мост исполнителя при этом выключается (`TB_SCAN_BRIDGE=0`), иначе были бы дубли.
Старый `./tb bybit read scan --watch` (Monitor) работает как прежде; одновременно со службой его запускать не нужно.

## Фабрика меток: сервис `labels` (R1)
`python -m tb.labels.service run` (запускает супервизор) входит в наборы `paper`, `testnet`, `trade` (`config/platform.json`). Читает хвост `runtime/hot_events.jsonl`, пишет сигналы, признаки, исходы и прогоны теневых политик в `state/knowledge.sqlite`, свечи берёт из публичного REST Bybit (ключи не нужны и не передаются; настройки `config/labels.json`, политики `config/shadow_policies.json`, геометрия `config/geometry.json`). Устройство: `docs/ARCHITECTURE.md`, раздел «Фабрика меток».
- **Запуск и остановка.** Вместе с платформой: `./tb up` / `./tb start` и `./tb down` / `./tb stop`. Только этот сервис среди прочих: `./tb up --services exec,scan,labels`. Без платформы вручную: `python -m tb.labels.service run [--max-seconds N] [--root DIR]` (нужен `PYTHONPATH=src`). Отключить разметку, не убирая сервис: `"enabled": false` в `config/labels.json` (сервис живёт, heartbeat идёт, захвата и разметки нет). Лог: `./tb logs labels` (`runtime/logs/labels.log`). Останов по Ctrl+C/SIGTERM корректный, очередь и курсор лежат в базе и подхватываются при следующем старте.
- **Статус.** Heartbeat `runtime/platform/labels.hb.json` (допустимая задержка 120 с): `captured_24h`, `labeled_24h`, `pending`, `due`, `failed_24h`, `no_data_24h`, `rate_limited_24h`, `req_per_min`, `bad_lines`, `last_error`, `db_mb`, `missing_share_24h`, `warnings`. `./tb status` красит сервис жёлтым, если `due` больше 500 (пороги `config/labels.json:warn`), если `failed_24h` больше 5% захваченных за 24 ч, при `DB_CORRUPT` и `W_LABELS_SYNC_DIR`; в шину сервис ничего не пишет, мозг его состоянием не будится.
- **Команды `./tb labels`** (реализуются в `tb.labels.cli`, формат и коды по Requirement 12.5 и 13 спеки):
  - `status`: heartbeat, очередь, размер базы, прогресс догрузки;
  - `stats [--since D] [--by policy|type|...]`: статистика политик (n, заполнения, win, средний `r_net` +- se, PF, MFE/MAE в R, p и порог Бонферрони по числу включённых политик) и базовая частота исходов по типам сигналов; версии политик не смешиваются;
  - `coverage [--since D]`: статусы сигналов и доля пустых признаков среди размеченных (порог 10%, `config/labels.json:coverage_fields`);
  - `show KEY`: JSON сигнала с признаками, исходами и прогонами политик (код 0; нет ключа: 1);
  - `backfill --since YYYY-MM-DD`: захват сигналов из `runtime/hot_events.jsonl` с даты и постановка созревших в очередь. Сама команда только ставит сигналы в очередь (`pending`), размечает работающий сервис с соблюдением `max_rps` (5 запросов/с), возобновляется без дублей; прогресс виден в `status`. Признаки, недоступные задним числом (`fng`, `risk_off`), пишутся `null`. Оценка: около 21 тыс. сигналов за 6 дней, около 3 запросов на сигнал, порядка 3,5 ч;
  - `rerun --policy ID --since D`: заново прогнать политику (свечи грузятся заново, они в базе не хранятся) для сигналов с даты; строки пишутся для текущей `policy_ver`;
  - `backup`: копия базы без остановки сервиса (см. ниже);
  - `verify`: `PRAGMA integrity_check` и проверка, что у каждого сигнала `done` есть исходы трёх горизонтов и строки всех подходящих включённых политик текущих версий; печатает число нарушений, код 0 только при нуле.
- **Резервная копия.** При маркере `state/knowledge.v2` `./tb labels backup` делает проверенную копию тем же путём, что `./tb knowledge backup` (имя `knowledge-<время>-owner.sqlite`), а во время восстановления отказывает. Без маркера (R1) `./tb labels backup` делает копию через `sqlite3.Connection.backup` (согласованный снимок при работающем сервисе) в `state/backups/knowledge-YYYYMMDD.sqlite` (до трёх попыток при `PermissionError` на Windows). Файл `state/knowledge.sqlite` вместе с `-wal`/`-shm` не копировать руками при работающем сервисе. Базу нужно беречь: из свечей прошлое восстанавливается только за последние ~30 дней, поэтому метки старше этого срока без копии не воссоздать.
- **Папка синхронизации (`W_LABELS_SYNC_DIR`).** SQLite в режиме WAL ломается в папках OneDrive, Dropbox, iCloud, Google Drive и на сетевых путях (`\\...`): файлы `-wal`/`-shm` синхронизируются отдельно и база портится. Если путь к `state/` содержит такой маркер, сервис пишет предупреждение в heartbeat (`warnings`) и `./tb status` показывает жёлтый. Действие: перенести проект (или `TB_ROOT`) вне синхронизируемой папки; копии (`state/backups/`) для синхронизации безопасны.
- **`DB_CORRUPT`.** С R2 (маркер `state/knowledge.v2`, его создаёт цикл обучения) карантина и пустой новой базы нет: сервис меток останавливает записи и ждёт восстановления, восстанавливает базу сервис `learnloop` (раздел «Цикл обучения» ниже). Без маркера (поведение R1): база не открылась как SQLite, файл переименовывается в `state/knowledge.corrupt-<unixtime>.sqlite`, создаётся пустая новая база, `last_error`/`warnings` несут `DB_CORRUPT`, статус жёлтый. Действие: остановить сервис, сохранить `knowledge.corrupt-*.sqlite`, восстановить последнюю копию из `state/backups/` (положить на место `state/knowledge.sqlite` при остановленном сервисе), затем `./tb labels backfill --since <дата копии>` для сигналов после неё.
- **Коды выхода сервиса.** 2: вторая копия на том же корне (блокировка `runtime/platform/labels.lock`, живой pid), супервизор в первые 10 с её не перезапускает; 4: `SCHEMA_MIGRATION`, миграция схемы базы не применилась (транзакция откатана, схема прежняя; чаще всего база новее кода или файл занят), супервизор тоже не перезапускает (`fatal_codes` 2 и 4). При 4 смотреть `./tb logs labels`, не удалять базу.
- **Ограничения биржи.** При HTTP 403/429 сервис ставит запросы на паузу 60 с, метки остаются `pending` без траты попытки (`rate_limited_24h` в heartbeat). Сбой сети: повтор 2/5/15 с, затем отсрочка метки на 30 мин, после 5 попыток `failed`.
- **Окружение.** Сервис запускается без `BYBIT_*`, `ANTHROPIC_*`, `DEEPSEEK_*`, `OPENAI_*` и без переменных `*_API_KEY`, `*_SECRET`, `*_TOKEN` (и сам вычищает их при старте).

## Сводный рынок: перенос `runtime/intel/xflow.json` (R1.7)
Файл `runtime/intel/xflow.json` (стены других бирж и ликвидации за 5 мин для сторожа позиции через `core.flowdoc.xlive_for`, сводка `xflow.summary` в `facts.json`) пишет ровно один производитель: поток `tb.xdata.xstream` в сервисе `intel` (`compat_xflow=false`, поставка) или сводный рынок `tb.cmkt.compat` (`config/cmkt.json: compat_xflow=true` при `enabled=true`; поле документа `src`: `xstream` или `cmkt`). При флаге сервис `intel` поток `XStream` не запускает; битый `config/cmkt.json` флаг не включает (сервис `cmkt` с ним не стартует, писателем остаётся `xstream`). Охват совместимого документа повторяет `xstream`: до 8 монет (позиции и планы, запросы структуры, BTC/ETH/SOL, затем топ по обороту из фокуса), рынки `okx`, `bitget`, `binanceusdm` (perp), стакан обрезан до глубины `xstream` (Binance 20 уровней, Bitget 15, OKX без обрезки), ликвидации только Binance, запись раз в 2 с.
- **Переключение.** (1) `compat_xflow=false`: сервис `cmkt` работает параллельно не меньше 24 ч, в `./tb cmkt status` нет `BUDGET` и в сводке не меньше 4 бирж. (2) Поставить `"compat_xflow": true` в `config/cmkt.json` и перезапустить платформу (`./tb restart`): флаг читают при старте и `intel`, и `cmkt`, поэтому перезапуск обоих сразу исключает двух писателей. (3) Проверить: `./tb cmkt status` (heartbeat `compat_xflow: true`, `compat_err` 0), в `runtime/intel/xflow.json` `"src": "cmkt"` и `ts_epoch` не старше нескольких секунд, по открытой позиции `xlive_for` даёт данные (страница позиции, досье мозга `xflow`/`deriv.x`).
- **Откат.** `"compat_xflow": false` и перезапуск (`./tb restart`, обязательно с `intel`: он снова поднимет `XStream`). Документ `xstream` перезапишет файл в течение 2 с.
- **Ожидаемое следствие: больше пробуждений `BOOK_WALL`.** У `xstream` OKX и Bitget стоят в `down` (`RequestTimeout` WS `ccxt.pro`), у `cmkt` они работают, поэтому сторож позиции начнёт получать и их стены (так и было задумано у `xstream`). Стены Binance остаются как прежде (стакан 20 уровней). Риск — расход токенов, а не торговля: пробуждений не больше 12 в час на позицию и пауза 10 мин между повторами `BOOK_WALL` (`docs/HARNESS.md`, «Защита прибыли»). Если пробуждений стало заметно больше (журнал `brain_wake_request` с кодом `BOOK_WALL`), это не сбой; решение о пороге стен — отдельной спекой.

## Цикл обучения: сервис `learnloop` (R2)
Устройство: `docs/ARCHITECTURE.md`, «Цикл обучения и rulebook»; правила в мозге: `docs/BRAIN.md`, «Правила rulebook»; спека `.opencode/specs/R2-closed-learning-loop/`. Сервис входит в наборы paper, testnet, trade, работает кодом без ключей и сети (модель — необязательно, через демон API-мозга, раздел «Модель в цикле обучения»), в торговлю не вмешивается. Поставка (решение владельца 6): `config/learnloop.json` `enabled=true`, `promotion.mode="auto"`. Обязательных действий владельца нет: прогрев, продвижение, откат и восстановление базы делает код; всё ниже — проверка и необязательная аварийная опция.
- **Что смотреть.** `./tb status`, строка «цикл обучения»: цвет, состояние, режим продвижения, прогрев (`готов` или невыполненные условия `promotion_ready`, например `DAYS`), работа цикла за сутки UTC. Жёлтый: `RULES_NO_EVENT` (доля решений без события > 0.2 за 7 суток), `WARMUP_STUCK` (прогрев не завершён 21 сутки), `AUTO_RESTORED` (7 суток после автовосстановления), `STALE` (нет успешного прохода). Красный: `WATCH_STALE` (цикл работает дольше 6 ч без успешного сторожа; правила при этом не применяются), `CHAIN_BROKEN`, `DB_CORRUPT`, `KNOWLEDGE_MIGRATION`; блок базы знаний добавляет `RESTORING` и `RESTORE_FAILED`. Логи: `./tb logs learnloop`.
- **Команды чтения.** `./tb knowledge verify [--quick]` (integrity_check, цепочка `rulebook_versions`, триггеры, маркеры; код 1 при красном), `./tb knowledge stats` (строки таблиц, размер, копии), `./tb rulebook list|show|verify` (версии, правила, `block_h`, режим применения `apply`/`why`), `./tb learn gate [--json]` (ступени A и B гейта этапа по накопленной истории), `./tb learn promotion` (текущий режим), `./tb memory lesson diagnose` (воронка «почему уроков 0», только чтение).
- **Копии.** Цикл сам делает проверенные копии (`daily`, перед миграцией `premigrate`, после смены версии rulebook `promote`/`rollback`, после записи владельца `owner`) в `state/backups/knowledge-<время>-<причина>.sqlite`; вручную `./tb knowledge backup`. Повреждённый источник не копируется (`SRC_CORRUPT`).
- **Восстановление базы (протокол).** Исполнитель — сервис `learnloop` (авто) или `./tb knowledge restore [--from FILE] [--ack-timeout 60]` (вручную, тот же протокол). Повреждение распознают только `SQLITE_CORRUPT`/`SQLITE_NOTADB` и провал `integrity_check`; нарушение `UNIQUE`, триггер или `database is locked` — обычная ошибка шага. Сервис меток, заметив повреждение, пишет сигнал `runtime/knowledge.corrupt`; цикл видит его за один проход `observe` (15 мин). Шаги: (1) маркер `runtime/knowledge.restoring` — все читатели перестают открывать базу (правила переходят в режим без применения, страница «Память» пишет «база восстанавливается»); (2) зарегистрированные писатели (`runtime/knowledge.writers/<pid>`: сервисы `labels` и `learnloop`, `./tb labels backfill|rerun`) закрывают соединение и пишут `runtime/knowledge.restoring.ack/<pid>`; ожидание не дольше `restore_ack_timeout_s` (60 с), иначе `ACK_TIMEOUT`; (3) выбор самой свежей копии, прошедшей `integrity_check` и проверку цепочек (или `--from`); (4) повреждённый файл переименовывается вместе с `-wal` и `-shm` (не удаляется); если у целевого пути остались `-wal`/`-shm`, подстановка не выполняется (`WAL_LEFT`: SQLite применил бы чужой журнал к копии); (5) подстановка копии, `meta.copy_ts`/`meta.restore_ts`, снятие маркера и сигнала. На Windows открытый файл не переименовывается, поэтому переименование и подстановка идут с повторами и паузой при `PermissionError`, а подтверждения писателей обязательны. Сбой протокола (`ACK_TIMEOUT`, `NO_COPY`, `COPY_BAD`, `WAL_LEFT`, исчерпание повторов) снимает маркер и пишет `runtime/knowledge.restore_failed.json`: красный статус до ручного `./tb knowledge restore`. Маркер, оставшийся после падения, сервис цикла завершает при старте. Потери: версии rulebook и записи чёрного списка новее копии; окна, задетые копией, закрываются кодом `RESTORED` без чёрного списка, статусы уроков меток назад не идут (сверка `reconcile`).
- **Если `restore` не прошёл.** Смотреть `runtime/knowledge.restore_failed.json` и `./tb logs learnloop`. `ACK_TIMEOUT`: какой pid не подтвердил (`./tb status`, `./tb logs labels`), повторить. `WAL_LEFT` или `PermissionError`: закрыть всё, что держит файл (антивирус, просмотрщик SQLite, второе окно `./tb labels backfill`), повторить; при остановленной платформе (`./tb down`) писателей нет. `COPY_BAD`: `./tb knowledge restore --from state/backups/<предыдущая копия>`.
- **Аварийные команды владельца** (необязательны, вне пакета `tb.learnloop`, каждая пишет `OWNER` в `learn_events` и считается вмешательством в ступени A гейта):
  - `./tb rulebook disable <rule_id>` — правило выключается новой версией `OWNER_DISABLE` (у правила в испытании испытание закрывается), условие в чёрный список бессрочно, копия;
  - `./tb rulebook disable-all` — сначала выключатель `runtime/rules_switch.json apply=false` (действует сразу и при повреждённой базе), затем версия без правил и бессрочный чёрный список; при недоступной базе команда сообщает, что запись версии нужно повторить после восстановления (код 1); применение остаётся выключенным до `./tb rulebook apply on`;
  - `./tb rulebook apply on|off` — только выключатель применения, версии не меняются;
  - `./tb rulebook unblock <block_h>` — снять запрет чёрного списка (ключ — семейство условия, его показывают `./tb rulebook list|show`);
  - `./tb learn promotion off|auto` — аварийная остановка и возврат автопродвижения (меняется только `promotion.mode` в `config/learnloop.json`, файл проверяется загрузчиком до и после записи; сервис перечитывает конфиг сам);
  - `./tb memory lesson reject <L-id>` — отклонить урок меток: урок `rejected`, открытое испытание закрывается, неактивное правило отклоняется, активное не трогается (его выключает `rulebook disable`), условие в чёрный список бессрочно. Прочие команды `memory lesson` для уроков меток отвечают `BAD_SRC`.
- **Вкладка «Память»** (дашборд, раздел «Мозг», `/brain/memory`): случаи, уроки (статус, источник, n, эффект с интервалом), путь «кандидат → урок → испытание → правило → версия», действующий rulebook, ожидающие правила (`READY`, `MAX_ACTIVE`, `LOSS_CAP` со сроком), доля отсутствующих признаков и решений без события; n < 30 помечено. Кнопки: «Отклонить урок» (без диалога), «Отключить правило» и красная «Отключить все правила» — только через единый диалог «принимаю риски» (список последствий, без токена и фраз). Кнопок «подтвердить урок» и «продвинуть правило» нет.
- **Выключить цикл.** `"enabled": false` в `config/learnloop.json` (сервис живёт и пишет heartbeat «выключен», базу не трогает); выйти из режима v2 (снять маркер `state/knowledge.v2` после копии) — `./tb knowledge disable-v2`, только при `enabled=false`.

## Переключение случаев и уроков на SQLite (R2.9b)
Случаи (`state/cases.jsonl`) и уроки (`state/lessons.jsonl`) переносятся в таблицы `case_rows` и `lesson_rows` базы `state/knowledge.sqlite` (та же хеш-цепочка, тот же фасад `memory.cases`/`memory.lessons`; спека `.opencode/specs/R2-closed-learning-loop/`, Requirement 3). Где лежат данные, решает маркер `state/memory.store` корня (JSON `{"store": "sqlite", "ts": …, "by": "migrate"}`; нет файла — `jsonl`): `store` — свойство данных корня, а не репозитория. Маркер пишут только `./tb knowledge migrate`, `export-jsonl` и `store-marker`, вручную не править. Ключ `store` в `config/memory.json` — только переходная совместимость для корня проекта: если маркера нет, корень проекта берёт `store` оттуда (так платформа, переключённая кодом до маркера, остаётся на `sqlite`), а `./tb knowledge verify` и `./tb status` показывают жёлтый `STORE_IN_CONFIG` с подсказкой «выполните `./tb knowledge store-marker`». Любой другой корень (временные корни тестов, копии `state/`) без маркера работает на `jsonl`, `config/memory.json` на него не влияет. Правила, версии rulebook и испытания от `store` не зависят. Досье мозга: `./tb brief` содержит блок `memory`, как раньше. После первой закрытой сделки `./tb knowledge verify` показывает выросшее число `case_rows`, а `cases.jsonl` не появляется.

**Возврат на JSONL** (если что-то не так после переключения): `./tb down`; при жёлтом `SPOOL_PENDING` сначала `./tb knowledge replay-spool`; по желанию проверочный экспорт без переключения `./tb knowledge export-jsonl --out runtime/r29-export-check --text`; затем `./tb knowledge export-jsonl --text` — файлы `cases.jsonl` и `lessons.jsonl` строятся из таблиц (формат прежний, цепочка пересчитана, записи после переключения на месте), свёртка сверяется с базой, и только после успеха маркер `state/memory.store` получает `store="jsonl"`; `./tb memory verify` — `ok: true`; `./tb up`. Строки в `case_rows` остаются (таблицы append-only), правила не отключаются. Файлы `*.pre-r29` — копии на момент переноса; перед следующим `migrate` их нужно убрать в `state/backups/` (иначе `PRE_EXISTS`); повторный перенос дописывает только строки, появившиеся после возврата.

**Отказы и что делать:**
- `PLATFORM_RUNNING` — что-то из платформы живо (причины перечислены в сообщении: `supervisor pid`, `сервис <имя> pid`, `heartbeat <имя> (N с)`, `писатель базы pid`). `./tb down`, `./tb status`; heartbeat с мёртвым процессом не мешает, свежий heartbeat живого процесса — остановить этот процесс (часто отдельный `./tb labels backfill` или `./tb dash`). Ничего не изменено, повторить шаг 4.
- `SPOOL_PENDING` — в `state/knowledge.spool.jsonl` есть записи, не попавшие в базу (база была недоступна при `store="sqlite"`). `./tb knowledge replay-spool --text` (идемпотентно; конфликты остаются в очереди, код 1 — передать файл разработке), затем повторить команду. При `store="jsonl"` очередь не применяется: файл не удалять, передать разработке.
- `JSONL_APPEARED` — перенос выполнен (`store="sqlite"`), но за время проверки в `state/` появился `cases.jsonl` или `lessons.jsonl`; в `./tb knowledge verify` тот же код жёлтым. Значит, кто-то пишет в обход фасада или работает процесс со старым кодом. Платформу не запускать; найти и остановить процесс (`./tb status`, диспетчер задач); файл не удалять, а перенести в `state/backups/r29-appeared/`; если в нём есть строки (`./tb knowledge migrate --dry-run` до переноса показывает их число), передать его разработке: эти записи в базу не попали.
- `DB_DIVERGED` — повторный перенос после возврата: строка базы с тем же `seq` отличается от файла (файл правили не дозаписью, или базу восстанавливали из копии). Перенос откатан, всё прежнее. Остаться на `store="jsonl"` (платформа работает как раньше), не удалять строки базы и не править файлы, передать разработке вывод `./tb knowledge migrate --dry-run` и `./tb knowledge export-jsonl --out runtime/r29-diverged`.
- `PRE_EXISTS` — остались `*.pre-r29` от прошлого переноса: убрать их в `state/backups/` и повторить. `ALREADY_SQLITE` — перенос уже выполнен. `LOCK_BUSY` — `cases.lock`/`lessons.lock` заняты писателем: платформа не остановлена. `BLOCKED` (`DUP_REV`, `BAD_SEQ`) — в файле одинаковые `(case_id, rev)` с разным содержимым или нарушен порядок `seq`: не переносить, передать разработке. `FOLD_MISMATCH`, `CHAIN_BROKEN` при переносе — откат, всё прежнее, передать разработке. `INDEX_FAILED` (в выводе «индекс похожих: НЕ СОЗДАН») — данные перенесены, поиск похожих работает медленнее: при остановленной платформе `./tb knowledge index-similar`.
- `CHAIN_BROKEN` в `case_rows` или `lesson_rows` после переключения (`./tb knowledge verify`, `./tb memory verify`) — новые записи случаев и уроков уходят в очередь `knowledge.spool.jsonl`, торговля и мозг работают. Порядок: `./tb down`; `./tb knowledge restore` (последняя проверенная копия) или `--from state/backups/<копия>`; `./tb knowledge replay-spool --text`; `./tb knowledge verify --text` и `./tb memory verify`; `./tb up`. Команды «перецепить» цепочку нет (Requirement 3.8).

## Модель в цикле обучения: роли `day_reviewer` и `retro`
Необязательная часть цикла (R2, вторая итерация; `docs/BRAIN.md`, «Цикл обучения и модель»). Без модели цикл работает полностью кодом.
- **Назначить профиль.** Роли общие; профиль берётся из действующих назначений (подписанный `state/brain/active.json`, без него `config/brain.json: shared_roles`). В поставке обе роли **без профиля** («не назначена»): модель не вызывается, цикл идёт кодом (`llm=false`), пока владелец не выберет профиль. `./tb brain role list` — строки `day_reviewer` и `retro` (`"assigned": false`, `primary: null`, пока не назначены). Назначить: `./tb brain role chain shared.day_reviewer --primary <профиль> [--fallback <профиль>]` (и `shared.retro`), или дашборд «Система → Настройки», «Кто думает»: строка роли «модель не назначена» → выбрать основную модель → «Применить». Это новая подписанная ревизия `active.json` с записью в `state/brain/swaps.jsonl`; назначения остальных ролей не меняются, в том числе если `active.json` создан до появления ролей. `./tb brain reload --from-config` для этого не нужен (он заменяет все цепочки поставкой, где роли цикла не назначены). Платная или локальная модель — выбор владельца; бюджет роли — `./tb brain role budget`.
- **Что значит `LLM_FALSE`.** Событие цикла в `learn_events` (шаг `day_review`, `retro` или `llm_collect`; `ref` — `D-YYYYMMDD` или `W-YYYY-WW`): модель за эти сутки или неделю не привлекалась, цикл отработал кодом (`llm=false`). Это не ошибка и в `./tb status` цвет не меняет. Причина в поле `why`: `NO_DAEMON` (демон API-мозга не запущен или heartbeat устарел), `PROTECT` (мозг в «только защите»), `BUDGET` (бюджет исчерпан), `NO_ROLE` (роль не загружена, не назначена или нет допустимого профиля), `TIMEOUT` (ответа нет за 600 с), коды ответа демона (`NO_ASSIGNMENT`, `NO_PROFILE`, `EXPIRED`, ошибка вызова). Остальные коды тех же шагов: `LLM_SUBMIT` (задание поставлено), `LLM` (ответ принят, в теле номера принятых и отклонённых элементов с кодами), `LLM_REJECT` (ответ отклонён целиком, неверная форма). Смотреть: таблица `learn_events` (`./tb knowledge stats` — число строк) и `./tb logs learnloop`; расход — `./tb llm usage` и строка `llm_usd_learn_day` в `./tb brief`.

## Страница «Учится ли мозг» (R0.2)
Устройство: `docs/ARCHITECTURE.md`, раздел «Страница «Учится ли мозг»»; спека `.opencode/specs/R0.2-learning-page/`. Страница только читает: торговлю, лимиты, план и журнал не меняет, отдельных прав и ключей не требует.
- **Как открыть.** Платформа запущена (`./tb up`, сервис `dash`, порт 8765): в дашборде раздел «Мозг», вкладка «Учится ли мозг» (адрес `/brain/learning`). Режим берётся из переключателя в шапке; режимы paper, testnet, live не смешиваются, выбор «все» показывается как paper с пояснением. Запрос уходит при заходе, смене режима, возвращении связи и закрытии новой сделки, периодических запросов нет. Отладка интерфейса без сервера: `?learning=mock|mock-few|mock-confirmed|mock-empty|mock-computing`.
- **Как читать вердикт.** Сверху одно из трёх слов. «Данных мало»: закрытых сделок мозга меньше 30, выводов делать нельзя. «Разницы не видно»: сделок от 30, но нет доказанного улучшения (до 60 сделок сравнивать недавние с прежними нечем; дальше разница не вышла за случайный разброс, либо выросли нарушения правил, либо сделок стало слишком мало). «Улучшение подтверждено»: недавние сделки (последние 50, но не больше n - 30) дали средний R выше прежних, разница значима (Уэлч, p ниже 0.05), доля нарушений правил не выросла и сделок в сутки не меньше половины прежнего. Предупреждение «стало хуже» показывается при значимом ухудшении, слово остаётся «Разницы не видно». Вердикт отвечает на вопрос «стало ли лучше, чем было», а не «прибыльно ли»: прибыль не доказана (`docs/RESEARCH.md`). Пороги (30 сделок, 0.05) берутся из `core/expstats.py` и в `config/learning.json` не настраиваются; применённые значения лежат в `verdict.params`. Сделки считаются только мозга: без `shadow`, без ручных (тег `manual*`), без сделок без плана и без R; сколько отброшено, видно в `meta.excluded`.
- **Блоки и статусы.** Порядок в ответе: Результат (скользящий R по окнам 50 и 200, PF, доля комиссий), Мозг против теневой политики (сравнение за последние 14 дней с политиками из `config/shadow_policies.json`; не входит в вердикт, оговорки непарности и издержек подписаны на странице), Дисциплина (нарушения правил и ошибки по неделям), Пропуски (доля верных пропусков, упущенный ход в процентах цены после издержек, не в R), Выходы (MFE и доля забранного хода), Экономика (токены и USD на сделку и на R по неделям, журнал вызовов платформы целиком, не по режимам), Память против базы (Brier, точность и покрытие; ретро-тест `./tb memory backtest`), затем Уроки, Версии мозга «до/после» и Гипотезы (R2.6; до появления таблиц цикла — заглушка «появится на этапе 2»). Статусы блока: `ok` числа показаны; `few_data` числа показаны, но n меньше порога (30), выводов делать рано; `no_data` источника нет (причина в `reason`); `stage` блок появится на указанном этапе дорожной карты; `computing` блок памяти считается в фоне, придёт повторным сообщением (до 30 с ожидания, затем можно обновить страницу); `error` блок не собрался (`E_BLOCK`), остальные целы. Причины `no_data`: `no_trades` нет сделок режима, `no_cases` нет случаев в `state/cases.jsonl`, `no_path` нет пути цены (MFE) у сделок, `no_usage` нет журнала вызовов, `labels_off` базы меток нет или она пуста (сервис `labels` не писал, раздел «Фабрика меток»; штатное состояние до накопления данных), `mode_unknown` режим пропусков в журнале не определён (миграция пишет их как live, чужие цифры не подмешиваются), `no_whatif` у пропусков нет оценки «что было бы», `too_many_for_request` сделок больше `memory.max_trades`, память считается по расписанию (этап 3). `few_cases` у дисциплины и пропусков: меньше 30 случаев.
- **`config/learning.json`** (схема `tb.learning_cfg/1`, файл необязателен, без него действуют умолчания; пример и умолчания в `src/tb/learn/conf.py`): `verdict.recent_n` 50 (размер «недавних», 30..1000), `verdict.guard_trades_ratio` 0.5 (нижняя граница отношения числа сделок в сутки, 0..1), `windows` [50, 200] (окна графика результата и выходов, 1..4 целых 30..1000), `series_points` 120 (точек в ряду), `weeks` 8 (недель в блоках по неделям), `policy_days` 14 (окно сравнения с политиками), `baseline_policies` [P5, P6] (базовые политики для итога сравнения), `memory.max_trades` 600, `memory.budget_s` 3.0 (сколько ждать расчёт памяти на запросе), `memory.ttl_s` 900, `cache.ttl_s` 60, `cache.min_interval_s` 10, `pf_bootstrap.b` 500, `.seed` 20261102, `.level` 0.9 (интервал PF бутстрепом, детерминирован). Лимиты, плечо, размер и уровень риска в этот файл не входят и от него не зависят. Правка применяется без перезапуска (подпись файла входит в ключ кеша; пересчёт не чаще `cache.min_interval_s`).
- **Предупреждения** (поле `meta.warnings` ответа, страница показывает только часть словами). `E_CONF:<поле>`: поле `config/learning.json` неизвестно или вне диапазона, взято умолчание (`E_CONF:file` файл не читается как JSON-объект, `E_CONF:schema` не та схема); остальные поля действуют. `E_LOAD:<источник>` (`trades`, `cases`, `skips`, `usage`): источник не прочитался, блоки на нём пустые, смотреть `runtime/logs/dash.log` (в журнал идёт только класс исключения). `usage_truncated`: журнал вызовов длиннее лимита чтения, экономика по хвосту. `mixed_rules`: в окне разные версии правил (`rules_key`), вердикт не блокируется. `capture_gt_1`: доля забранного хода больше 1 из-за округления пути. `series_thinned`: ряды прорежены, чтобы ответ уложился в 64 КБ.
- **Если страница пустая или «Считается…» не проходит.** Нет связи: проверить сервис `dash` (`./tb status`), страница переподключится сама. «Не удалось собрать отчёт» (`ok: false`): причина в `runtime/logs/dash.log`. Блок памяти висит в `computing` дольше 30 с: расчёт идёт в фоне до конца, обновить страницу позже (готовый результат лежит в кеше 15 минут).

## MCP и мозг как сервисы

## День: старт, закрытие, перенос, итог (WP14)
Кнопки «Старт»/«Стоп» дня запускают шаги S1-S9 / C1-C8 (`docs/LIFECYCLE.md`). Состояние: вкладка «День» или `./tb day status` (`list`, `report [ID]`, `preflight [--mode M]`, `checklist` = сухой прогон того, что сделала бы остановка; всё только чтение).
Остановка может висеть в `closing`: ждёт ответ владельца о переносе (15 минут, без ответа позиция закрывается), ответ мозга (90 с) или подтверждение закрытия исполнителем (120 с). Если закрытие не подтверждено, день остаётся `closing` с красным баннером: проверить позиции на бирже,
затем кнопкой «Прочитал» (`report.ack`) с пометкой «разобран вручную». Итог дня (`state/days/<D-id>/report.md`) приходит баннером и событием `day_report`; уведомления ОС включает владелец сам: вкладка «Уведомления» дашборда или `./tb notify status|on|off|set|test` (приоритет у `state/control/notify.json`, без него действует `config/lifecycle.json: notify.os`; категории, тихие часы, антиспам: `docs/NOTIFICATIONS.md`).
Перенос через сутки: политика уровня риска (1 никогда, 2-3 подтверждает владелец, 4-5 решает агент), жёсткие условия K1-K8 проверяет код; без доступного мозга перенос невозможен (K8). После перезапуска платформы при идущем дне торговый флаг выключен до подтверждения: вкладка «День», кнопка «Возобновить день» (`day.resume`, только paper/testnet; `./tb control cmd day.resume --wait`).

## Интеграция: первый сквозной запуск (paper)
Пошагово: `docs/QUICKSTART.md`, подключение провайдера LLM: `docs/PROVIDERS.ru.md`; помощник настройки: `./tb setup [--check]`, ключи биржи: `./tb setup bybit --profile read|trade|testnet`; сквозной прогон без вашего счёта: `./tb smoke` (результат: `docs/spec_v2/SMOKE_RESULT.md`).
- Наборы по умолчанию (paper, testnet, trade): `exec, scan, feed, context, intel, sync, dispatch, ctl, dash`. `context` (`tb.platform.contextsvc`, обёртка над `marketdata/context.py`: деривативы, DVOL, индекс страха, макро-блэкаут; публичные источники, без ключей, сбой источника = degraded, не падение) пишет `runtime/context.json` и heartbeat каждые `config/platform.json: context.poll_s` (15 с); `sync` (`tb.platform.syncsvc`) раз в `sync.interval_min` (5) минут читает баланс ТОЛЬКО ключом `read` (launcher грузит его в процесс сервиса) и обновляет `state/portfolio.json`: при ошибке или без ключа портфель не трогается и помечается «устарело» (`runtime/platform/sync.state.json`); расхождение больше `sync.max_dev_frac` (10%) не применяется, уходит `reconcile_alert equity_mismatch`, принять значение: `./tb sync confirm`; высшая отметка растёт только после `sync.hwm_confirm_reads` (2) подтверждающих чтений подряд. P10: `levels.json` нужен, только когда есть планы или позиции. Ранее набор paper был `exec, scan, feed, dispatch, ctl, dash`: сервис `feed` (рыночный фид BTC/ETH/SOL, публичный WS Bybit) пишет `runtime/market.json`; без него в досье нет блока `market`, а план дня мозга отклоняется как `NO_DATA_PLANS`.
- Мозг отвечает на задания жизненного цикла: файлы `state/brain/jobs/L-*.json` (kind=lifecycle) берёт тот же демон `brain run` (`brain/lifejobs.py`), вызывает `Runner.ask_role` и пишет `L-*.result.json`; захват `L-*.claim` снимается при старте демона.
- Досье мозга получило блоки `limits`, `risk_level`, `paper_history` (только числа); `./tb exp stats --by agent|model` режет сделки по тегам шлюза; события `brain_swap` и `limit_hit brain_down` эмитятся.
- `./tb plan submit` (прямой путь чата) пишет в аудит шлюза запись `agent=cli` и добавляет предупреждение `W_CLI_BYPASS`; пока платформа ведёт день, не-paper план без торгового флага отклоняется `E_TRADING_*`.
- `./tb test` идёт параллельно по модулям (`-j N`, по умолчанию число процессоров; `-j 1` — один процесс), медленный набор (нагрузочные тесты, пороги скорости) — только `./tb test --slow` (`TB_SLOW_TESTS=1`); подробнее `docs/ARCHITECTURE.md`, «Тесты». Он ограничивает каждый тест по времени (`TB_TEST_TIMEOUT`, 180 с; на POSIX), пропускает тесты с локальным сервером, если localhost-сокет недоступен (песочница), и сверяет реальные `state/`, `config/`, `runtime/` до и после прогона (`TB_TEST_NOGUARD=1` отключает сверку).
