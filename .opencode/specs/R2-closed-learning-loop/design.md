# Design

## Overview

Цикл обучения реализуется пакетами `tb.knowledge` (хранилище цикла и, во второй итерации, перенос и поиск), `tb.learnloop` (логика цикла), чистыми модулями `tb.logic.learn_cond` (словарь признаков и сравнения) и `tb.logic.learn_rules` (правила) и сервисом платформы `learnloop`. Имена выбраны так, чтобы не путаться с уже существующими `tb.logic.conds` и `tb.logic.rules`. Цикл читает метки R1, при закрытии каждого кластера один раз записывает его прогоны в неизменяемую таблицу `cluster_runs` и все дальнейшие расчёты ведёт только по ней, по выборкам окна с границей `cut_ts`: раз в неделю строит кандидатов кодом из меню срезов, проверяет их на окне поиска и на holdout фиксированной длины вне выборки (парный тест внутри кластера, поправка Бонферрони), создаёт уроки меток `hyp`, сразу регистрирует испытание правила `skip_when` на будущих снимках и по записанному критерию вводит правило в версионный rulebook; шаг сверки приводит статусы уроков меток к базе; сторож откатывает ухудшения.

Принципы: модель выбирает из словаря, числа и решения считает код; код ужесточает и откатывает, ослабить не может; владелец видит и имеет только необязательные аварийные пути.

## Объём первой итерации

Явное сокращение объёма (по замечаниям ревью; всё вынесенное сохранено в спеке как вторая итерация):

| Вынесено во вторую итерацию | Причина |
|---|---|
| Перенос случаев и уроков в SQLite, цепочки `case_rows`/`lesson_rows`, экспорт, очередь записей (Requirement 3, R2.9b) | Цикл не зависит от места хранения случаев и уроков (фасад `memory.*` остаётся). Перенос — самый рискованный шаг. Нужен этапу 3, не этапу 2 |
| Поиск похожих по меткам (Requirement 3.9–3.12) | Нужен этапу 3; в этапе 2 источник `labels` в досье выключен |
| Роли `day_reviewer`, `retro`, порт заданий (Requirements 12, 17) | Модель не нужна для замыкания цикла; меню срезов строит код. Вызовы модели добавляют зависимость от демона API-мозга (случаев API-мозга нет: 144 из 148 — `chat`), стоимость, нагрузку (R0.4) и поверхность атаки |
| Справочные уроки мозга, `pool_mode`, заморозка продвижения, условие по нарушениям, `shadow_hits`, меню по `utc_session` с тестом Уэлча (Requirement 18) | Справочные уроки правил не порождают; заморозке нужна история сделок не короче 21 суток; условие по нарушениям почти всегда `not_evaluable` и единственный потребитель `shadow_hits`; у сессии `overlap` не больше 6 кластеров в сутки — мощность недостижима |
| Правила `size_cap`, `require_confirm` | Решение владельца 3 (только запрет входа); `require_confirm` не испытуем на политиках R1 |
| Хеш-цепочки на остальных таблицах | Цепочка только у `rulebook_versions` (аудит правил); остальные таблицы цикла защищены триггерами |
| Метрики `win_rate`, `stop_hit_share`, `err_share` и пары условий | Первая итерация: метрика `mean_r`, одиночные условия (K ≤ 17, прозрачная поправка) |

Удалено ревизиями 2026-11-03 без переноса: стадия подтверждения урока меток через `lessons.refresh` с провайдером, кеш правил вне базы, перепроверка и срок действия вердикта, удвоение срока чёрного списка и отдельный cooldown для `dropped`, критерий суммы упущенной прибыли, отключение правила по доле отсутствующих признаков, статический поиск вызовов и счётчики в диагнозе, досрочный тест holdout, отдельные таблицы наблюдений, порог доли часов без сигнала. Причины — раздел «Ревизии 2026-11-03».

Что нельзя вынести: проверка вне выборки (holdout), испытание и сторож — без них цикл не замкнут и ужесточения нельзя вводить автоматически; защита базы и единое правило безопасности — без них сбой базы или надзора оставил бы безнадзорные правила.

## Ревизии 2026-11-03

### Первый раунд ревью

- **Критерий (г) `missed_r_max` удалён.** Сумма `max(r_without, 0)` по предельным хитам при σ ≈ 1.2R на 100 хитах около 34R даже при среднем −0.3R (E[max(X, 0)] ≈ 0.34R для X ~ N(−0.3, 1.2)), поэтому порог 5R недостижим и блокировал бы любое правило. Упущенную прибыль уже учитывает критерий (а): среднее `r_without` (включая положительные хиты) не выше −`min_effect_r` и хуже базы.
- **Claim кода содержит `effect`.** `memory/lessons.py:validate_claim` (строки 122–137) требует `effect` — число 0..10.
- **`lessons.create` для меток.** Сейчас `create` (строки 332–349) всегда вызывает `stats()` по пулу сделок мозга; новые параметры `evidence_src`, `evidence_extra`; при `evidence_src="labels"` `stats()` не вызывается.
- **Гонка `_next_id`.** `_next_id` (строка 308) читает файл вне блокировки, а `_write` → `chain.append` (`memory/chain.py`, строка 82) берёт `FileLock` только на запись; колбэк `check()` вызывается под блокировкой до копирования записи и не предназначен для её изменения. Выбран явный захват `with FileLock(lessons_lock(root))` вокруг `_next_id` и `_write`; `FileLock` (`core/filelock.py`) реентерабелен по (путь, поток).
- **Общие точки применения правил** — `brain/cands.py:candidates` (через `brief.build`) и `gateway/catalog.py:h_submit`.
- **Упрощения** — без стадии `confirmed` через `refresh`, без кеша правил, без перепроверки, без экспоненты чёрного списка, без потери входов по решениям мозга, без отключения по паритету.

### Второй раунд ревью

- **Мощность** — holdout фиксированной длины, парный тест внутри кластера, `n_target` = 150, целевая мощность ≥ 0.5 — критерий приёмки задачи 9.
- **Снимки `cluster_runs`** — все расчёты по ним; таблицы `trial_obs`/`watch_obs` удалены (их числа — агрегаты снимков, отдельные таблицы были бы вторым путём записи).
- **Активный набор в критерии**, `LOSS_CAP`, учёт простоя платформы, одна функция разрешения события, автовосстановление только сервисом цикла, исправление ключа оборота меток, условие по нарушениям во вторую итерацию.

### Третий раунд ревью

- **Окна и поздно закрытые кластеры.** Кластер закрывается до 48 часов после своего часа; расчёт «на сейчас» по `closed_ts ≤ now` давал бы разный результат при повторе и `SAMPLE_CHANGED` без повреждения. Теперь каждая выборка — строки с `t0 ∈ [a, b)` и `closed_ts ≤ cut_ts`, `cut_ts = b + cluster_close_max_h`, а расчёт выполняется не раньше `cut_ts`: к этому моменту все кластеры окна закрыты, и повтор даёт тот же хеш. Цена — задержка 48 часов у меню, holdout, вердикта и точек сторожа (учтена в сроках).
- **Пересечение правил.** `lessons.overlap` (`memory/lessons.py`, строки 184–190) проверяет только общие признаки и для условий на разных признаках всегда возвращает `True`; по нему почти любое продвижение закрыло бы все испытания. Пересечение считается по строкам `cluster_runs`: доля прогонов-хитов испытания, которые отсекает продвинутое правило, выше `overlap_share_max` (0.5).
- **Меню.** Условия шире `max_trade_loss_share` (0.3) прогонов отсеиваются `TOO_BROAD` (заменяет `NO_CONTRAST`). `utc_session` убран из меню: час целиком в сессии, пар нет, а у сессии `overlap` (13–16 UTC) не больше 3 часов × 2 стороны = 6 кластеров в сутки — тест Уэлча при таком потоке бессилен. В первой итерации остаётся только парный тест; K = 6 × 2 + 5 = 17.
- **Ожидание продвижения на уровне правила.** Испытание закрывается вердиктом и освобождает место в `max_parallel`. Правило ждёт без срока по готовности и лимиту `max_active_rules`, по `LOSS_CAP` — не дольше `loss_cap_wait_days` (14), затем `rejected` (`LOSS_CAP`) без чёрного списка. Срок действия вердикта `promote_valid_days` и `PROMOTE_STALE` удалены: проверка была верной, ожидание по готовности не ухудшает её; ограничение нужно только там, где ожидание может быть вечным при заполненном наборе.
- **Восстановление базы**: повреждённый файл переименовывается вместе с `-wal`/`-shm`; подстановка копии только при отсутствии `-wal`/`-shm` рядом (иначе SQLite применил бы чужой журнал к копии).
- **`resolve_event`** берёт только события видов области применимости: у `scanner_signal` с `d.kind` `idea_stale`/`idea_level` (`brain/brief.py`, строки 1416–1417) нет рыночных полей.
- **Сверка статусов.** Вместо вызова `transition` по событию — идемпотентный шаг, приводящий уроки меток к `rule_rows`/`trials`; переживает падение между записью версии и переходом урока и восстановление базы из копии.
- **Отклонение урока меток владельцем** описано полностью (Requirement 5.12) и реализуется после правил и сторожа (задача 16).
- **Упрощения**: один механизм запрета повтора — чёрный список (`dropped_cooldown_days` удалён); `shadow_hits` и меню по сессиям — вторая итерация; порог `max_gap_share` удалён (простой сканера просто не даёт кластеров теста, а срок `max_days` и `UNREACHABLE_N` уже ограничивают испытание); `rule_eval` пишется только после ранних проверок шлюза; смена `ctx_ver` во время holdout — `CTX_CHANGED` без запрета повтора; `expires_ts` урока меток `null` до `confirmed`.

### Четвёртый раунд ревью

- **Поля шины.** `core/bus.py:D_FIELDS` (строки 108–112) и `NUM_KEYS` публикаторов (`platform/scansvc.py:32-34`, `executor/scanbridge.py:16-17`) не содержат `chg_24h_pct` и `turn_24h_musd`: признак `chg_24h_pct` и `coin_class` по обороту на стороне мозга не вычислялись бы. Поля добавляются (задача 33, волна 1); `coin_class` монеты вне справочника без оборота — `None`; тест паритета идёт через реальный путь шины.
- **Восстановление на Windows.** Открытый файл нельзя переименовать: каждый держатель соединения закрывает его по маркеру и пишет подтверждение; цикл ждёт подтверждений живых процессов не дольше 60 с.
- **`RESTORED`.** После автовосстановления строки `cluster_runs`, закрытые позже копии, теряются и могут прийти заново; окна с `cut_ts` позже копии закрываются `RESTORED` без чёрного списка и без ошибки целостности.
- **Статусы и окна.** Любое терминальное состояние правила выводит урок из `hyp`; окно испытания `[start_ts, deadline_ts)`, `inconclusive` не раньше `deadline_ts + 48 ч`; смена `ctx_ver` во время испытания — `CTX_CHANGED`; `cut_ts = b + cluster_close_max_h + observe_s`, `b` по границе часа; первичный ключ `cluster_runs` с `policy_ver`; `DUP_ACTIVE` смотрит и правила `trial`/`active`.

### 2026-11-03, при реализации: найдено сквозным тестом задачи 22

- **Ключ чёрного списка — семейство условия `block_h`.** Запись по точному `cond_h` (условие вместе с порогом) не держала запрет: меню фиксирует порог числового признака квантилем окна (q80/q20), квантиль каждую неделю сдвигается, и отклонённое условие (например, `TRIAL_REJECT` для `spread_bps >= 8.2792`) через несколько суток возвращалось с порогом `8.20626` — даже бессрочно запрещённое владельцем (`OWNER_DISABLE`, `OWNER_REJECT`). Нарушало Requirement 7.14 и 11.5. Теперь ключ запрета — `block_h` (`tb.logic.learn_rules.block_h`, 16 hex): числовые признаки без порога `(feature, op)`, категориальные со значением `(feature, op, value)`, элементы отсортированы, плюс направление claim. Точный `cond_h` остаётся идентичностью правила (тело правила). `DUP_ACTIVE` тоже по семейству: условие меню или кандидат — дубль, если его `cond_h` или `block_h` совпадает с активным уроком меток, кандидатом в holdout или правилом `trial`/`active` (иначе активное правило `spread_bps >= 8.27` не мешало бы меню каждую неделю брать `spread_bps >= 8.20` и тратить слот испытания до `OVERLAP`). Проверки учитывают и прежние записи по точному `cond_h`, чтобы не потерять запреты; `./tb rulebook unblock` принимает `block_h`, его показывают `./tb rulebook list|show` и вкладка «Память» (поле `cond_h` правила, сменилось только значение). Регрессионные тесты — задача 16.

## Уроки меток: создание и статусы

Проблема (проверено по `memory/lessons.py`): `stats()` и `refresh()` считают по пулу сделок мозга, перезаписывают `evidence` и `conf`, отклоняют `hyp` при `n_closed >= reject_n_new` и `not supports`, продлевают срок по новым случаям мозга и подтверждают по `confirm_n_fast=15`. Вызов из `tick.sync_now` затёр бы урок меток, а `create` уже при создании посчитал бы `evidence` по сделкам мозга.

Решение:

- `lessons.create(root, cond, claim, created_by, all_cases, cfg, now, evidence_ids=None, status="hyp", evidence_src="brain", evidence_extra=None)`. Урок меток создаётся с `created_by="code"`. При `evidence_src="labels"`: `stats()` не вызывается; `evidence = dict(evidence_extra, src="labels")`; `conf` = `1 − exp(−n_eff / 10)`, `n_eff = n × |d| / (|d| + se)` по числам holdout (та же формула, что `conf_for`), не выше `conf_cap_reviewer`; `expires_ts = null` (срок появится при `confirmed`); проверка размера всей строки (4096 байт) до `_write`. При `evidence_src="brain"` поведение прежнее. Отдельный параметр срока не нужен.
- Читатели `expires_ts` (`lessons.applicable`, страница) считают `null` как «без срока»; `refresh` уроки меток не видит.
- Выдача идентификатора: `with FileLock(lessons_lock(root)): rec["lesson_id"] = _next_id(root); _write(root, rec)`.
- Бюджет `propose` (`memory/lessons.py`, строка 490: `made = sum(... l["created_by"] == "code" ...)`) исключает уроки `evidence.src="labels"`.
- Затухание: `conf_eff` возвращает `conf` без затухания для уроков `src="labels"` (проще, чем обновлять `evidence.last_ts` на каждом наблюдении).
- `lessons.transition(root, lesson_id, status, reason_code, now)`: под `FileLock(lessons_lock(root))` читает `read_all`, проверяет `evidence.src="labels"` и допустимость перехода (`hyp → confirmed|rejected`, `confirmed → expired`, `confirmed → rejected` только `OWNER`), для `confirmed` выставляет `expires_ts = now + ttl_confirmed_days` и `conf` по числам испытания (не выше 0.95, как `conf_for`), пишет через `_update`. Повтор с тем же целевым статусом ничего не пишет.
- `lessons.refresh`: набор `act` строится только из уроков `evidence.src != "labels"`; уроки меток не входят ни в пересчёт, ни в `k_active`, ни в противоречия, слияние `jaccard`, вытеснение. `tick.sync_now` не меняется.
- Лимит `lessons.max_active` считается раздельно по группам `src`.
- `lessons.applicable` (досье) показывает активные уроки обеих групп с пометкой источника.

Сверка статусов (`learnloop.reconcile`, раз в час): для каждого урока меток целевой статус по базе — испытание открыто или правило ждёт ⇒ `hyp`; любое терминальное состояние правила выводит урок из `hyp`: правило урока `active` или `disabled` (было активным) ⇒ `confirmed`; правило `rejected` с любым кодом (в том числе `CTX_CHANGED`, `RESTORED`, `OWNER`) ⇒ `rejected` с тем же кодом; `confirmed` с наступившим `expires_ts` ⇒ `expired`. Вызываются только переходы вперёд. Расхождение назад после восстановления базы из копии (урок уже `confirmed`/`rejected`, а в базе испытание открыто или правило ждёт): база приводится к уроку — испытание закрывается, правило `rejected` с кодом урока (для `confirmed` без активного правила — `NO_VERDICT`), `RECONCILE_MISMATCH` в `learn_events`; урок `hyp` без испытания и правила в базе регистрируется заново. Источник правды при движении вперёд — база; урок никогда не идёт назад.

Отклонение урока меток владельцем (задача 16): `transition(rejected, OWNER)`; открытое испытание закрывается `inconclusive`; не активное правило урока `rejected` (`OWNER`); активное правило не трогается; условие в чёрный список бессрочно (`OWNER_REJECT`); копия базы (`owner`). Остальные команды владельца для уроков меток отклоняются `BAD_SRC`.

Путь урока меток: `кандидат → поиск → holdout (7 сут + 48 ч) → hyp → (достижимость, регистрация испытания) → вердикт → promote ⇒ при продвижении правила confirmed; TRIAL_REJECT | NO_VERDICT | UNREACHABLE_N | LOSS_CAP | SAMPLE_CHANGED | CTX_CHANGED | RESTORED | BUDGET ⇒ rejected`.

## Единица наблюдения, кластеры, снимки и выборки окна

- Прогон — прогон политики проверки на сигнале; в метрики входят заполненные (`filled=1`), `hit` считается по признакам его сигнала.
- Кластер — ключ (`t0 // 3600`, `side`) по всему рынку. Внутри кластера: `in_r` — среднее R прогонов с `hit=1`, `out_r` — среднее прогонов с `hit=0`. Кластер теста — кластер с обеими группами; n везде — число кластеров теста.
- Тест — только парный: t-тест разностей `in_r − out_r` по кластерам теста; общая для кластера составляющая (движение рынка в этот час) вычитается. Остаточная автокорреляция соседних часов не учитывается (допущение).
- Закрытие: все прогоны кластера `status="done"`, но не раньше `labeled_ts + grace_min` последнего; иначе через `cluster_close_max_h` (48 часов после конца часа) с тем, что есть. При закрытии строки прогонов один раз записываются в `cluster_runs` (`INSERT OR IGNORE`); признаки `RULE_FEATURES` вычисляются при записи той же функцией `memory.features.rule_features`, что на стороне мозга (в том числе `coin_class` по обороту `ev.turn_24h_musd × 1e6`).
- Выборка окна: `t0 ∈ [a, b)` и `closed_ts ≤ cut_ts`; `a` и `b` выровнены на начало часа; `cut_ts = b + cluster_close_max_h + observe_s` — запас `observe_s` (15 минут) покрывает период шага `observe`, который записывает закрытые кластеры, поэтому к `cut_ts` последний кластер окна, закрытый по пределу 48 часов, уже в `cluster_runs`; расчёт не раньше `cut_ts`. Ниже «48 ч» означает эту границу. Окна: поиск `[b − 14 сут, b)`, `b` — последняя граница часа с `cut_ts ≤ now`; holdout `[holdout_start, holdout_end)`, `holdout_end = holdout_start + 7 сут` (по границе часа), тест в `cut_ts` окна; испытание `[start_ts, b)`, где `b` — конец часа `n_target`-го кластера теста по `(t0, key)`, вердикт в `cut_ts`; без набора `n_target` — окно `[start_ts, deadline_ts)`, `inconclusive` не раньше `deadline_ts + 48 ч`; сторож, потеря входов, `LOSS_CAP`, пересечение — окна с последней границей часа `b`, для которой `cut_ts ≤ now`.
- Хеш выборки: sha256 отсортированных строк выборки окна; вместе с `a`, `b`, `cut_ts` пишется в `evidence` или `trials`. Строки неизменяемы, граница записана, поэтому различие хеша означает повреждение: `SAMPLE_CHANGED` и ошибка целостности в `learn_events`. Исключение — любое восстановление из копии (автоматическое или ручное): строки, закрытые после копии, потеряны и могут быть записаны заново, поэтому окна с записанным хешем и `meta.copy_ts < cut_ts ≤ meta.restore_ts` закрываются `RESTORED` без ошибки целостности и без чёрного списка; окна с `cut_ts > restore_ts` продолжаются по `cluster_runs`, а потерянные после копии кластеры закрываются заново из `hot_events.jsonl`, если события там есть; окна с `cut_ts ≤ copy_ts` не затронуты.
- Бюджет события шины: `bus.MAX_EVENT_BYTES = 400` (`core/bus.py`, строка 77), `sanitize` при превышении выбрасывает самое длинное поле (строки 257–258). Задача 33 меняет порядок: сначала поля вне защищённого набора, `kind`, `dir` и поля признаков правил — в последнюю очередь; тест бюджета на худшем событии области `P2` (`oi_spike`/`liq_cascade` со всеми числовыми полями, символ 20 символов).
- Чёрный список: API `knowledge.store2.blocklist_put`/`blocklist_get` (задача 4) — единственный путь записи и чтения для меню, создания урока, `rules.derive`, регистрации и команд владельца.
- Смена `ctx_ver` (хеш входов теневых политик, `labels/policies.py`, строки 135–157: издержки и горизонты из `config/risk_profile.json`, автозащита и проскальзывание стопа из `config/exec_limits.json`, `shadow_ctx`, задержка; меняется, например, при правке профиля риска владельцем) закрывает текущий holdout и открытое испытание кодом `CTX_CHANGED` без чёрного списка, а окно меню начинается заново.
- `env_norm = "testnet" if signals.env == "testnet" else "mainnet"`; все фильтры по `env_norm`.

## Меню, скрининг и holdout

- Меню раз в `menu_every_days` (7) суток на окне `discovery_days` (14). Условия: шесть числовых признаков × (`>= q80`, `<= q20`) по квантилям прогонов окна и `coin_class` (5 значений без `unknown`; словарь `memory/cases.py:COIN_CLASSES` = `meme`, `major`, `alt_mid`, `alt_small`, `stock_token`, `unknown`). Максимум K = 12 + 5 = 17; фактический K — условия с n ≥ `min_n_menu`, не `TOO_BROAD` и не в чёрном списке. `cluster_runs` пересчитывает `coin_class` сам, поэтому `alt_small` присутствует с первого снимка. Медиана, `side` и `utc_session` в меню первой итерации не используются.
- `TOO_BROAD`: условие охватывает больше `max_trade_loss_share` (0.3) заполненных прогонов окна — такое правило не прошло бы критерий (б) испытания; квантильные условия охватывают около 0.2, `coin_class=major` может быть шире.
- `min_n_menu = ceil(n_target / (reach_factor × max_days) × discovery_days)` = ceil(150 / 24 × 14) = ceil(87.5) = 88 кластеров теста. Загрузчик конфига сверяет значение с формулой.
- Скрининг: n ≥ 88; средняя разница отрицательна в обеих половинах окна; одностороннее p < alpha / K; провалившие скрининг условия кандидатами не становятся и в чёрный список не пишутся (их проверка уже учтена в K следующего меню).
- Приём: до 3 кандидатов в сутки по возрастанию p; не принятые до следующего меню — `BUDGET`.
- Holdout: окно с момента приёма ровно `holdout_days` (7) суток; один тест в `holdout_end + 48 ч`; n ≥ `min_n_hyp` (30), иначе `N_TOO_SMALL`; порог alpha / K_h, K_h = 3 фиксировано; провал (`NO_OOS_SIGN`, `NOT_SIGNIFICANT`, `N_TOO_SMALL`) — запись в чёрный список на 14 суток; смена `ctx_ver` — `CTX_CHANGED` без записи.
- Повторный скрининг: окна соседних меню перекрываются на 7 суток. Вероятность ложного `hyp` за одно меню не выше alpha (скрининг, Бонферрони) × alpha / 3 (holdout) ≈ 0.00083; за 8 меню ≈ 0.0067 < alpha. Свойство 6 проверяет это симуляцией с фиксированным seed.

## Мощность и сроки

Допущения до замера задачи 9 (явно): σ разностей кластера около 1.2R (консервативно: вычитание общей части часа уменьшает разброс); типичное условие меню даёт около 20 кластеров теста в сутки (из 48 возможных: 24 часа × 2 стороны); истинный эффект −0.3R относительно базы, среднее базы около 0; доля потери входов типичного условия около 0.2 (ниже 0.3). Мощность одностороннего теста ≈ Φ(δ√n / σ − z). Ожидание закрытия 48 часов меняет сроки, но не n окон, поэтому на мощность не влияет.

| Ступень | n | Порог | z | δ√n / σ | Мощность |
|---|---|---|---|---|---|
| Скрининг, окно 14 суток | 280 | alpha / K = 0.05 / 17 ≈ 0.0029 | 2.76 | 4.18 | 0.92 (знак в обеих половинах ≈ 0.997) |
| Скрининг первого меню, окно 7 суток | 140 | 0.0029 | 2.76 | 2.96 | 0.58 |
| Holdout 7 суток | 140 | alpha / 3 ≈ 0.0167 | 2.13 | 2.96 | 0.80 |
| Испытание, `n_target` = 150 | 150 | `alpha_adj` = 0.05 / 5 = 0.01 | 2.33 | 3.06 | 0.77; с абсолютным порогом ≤ −0.1R (P ≈ 0.98) около 0.75 |
| Сторож, точка 200 (порог срабатывания) | 200 | 0.0167 | 2.13 | — | откат при среднем отсечённой части ≥ +0.18R |

Итог конвейера при допущенном потоке: 0.92 × 0.80 × 0.75 ≈ 0.55 (≥ 0.5, цель достигается); для первого меню (окно 7 суток) 0.58 × 0.80 × 0.75 ≈ 0.35. На нижнем пределе потока (88 кластеров теста за 14 суток, около 6.25 в сутки: скрининг n = 88 — Φ(2.35 − 2.76) ≈ 0.34, holdout n = 44 — 0.32, испытание 0.75) конвейер около 0.08: условия на пределе достижимости проверяются слабо, это принято явно.

Чувствительность к σ: при σ = 1.6R вместо 1.2R мощность ступеней падает до 0.65 (скрининг), 0.54 (holdout), около 0.47 (испытание), конвейер около 0.17 — поэтому задача 9 замеряет σ R прогона и среднее число прогонов-хитов на кластер теста (σ разности кластера ≈ σ прогона / √(хитов на кластер) при большом числе прогонов «вне условия»).

Критерий приёмки задачи 9: по замеренным σ и потоку мощность конвейера для медианного условия меню при эффекте −0.3R не ниже 0.5; иначе до приёмки пересматриваются `holdout_days`, `alpha`, `n_target`, `max_days` (и с ними формула `min_n_menu`).

Сроки (от начала накопления меток, с задержкой закрытия 48 часов на каждой выборке): первое меню на 9-е сутки (окно `[0, 7 сут)`, `b` на 7-х сутках); `hyp` около 18-х суток (holdout `[9, 16)` сут, тест на 18-е); полное окно 14 суток — с меню 16-х суток; испытание при 20 кластерах теста в сутки — 7.5 суток, на нижнем пределе 150 / 6.25 = 24 суток, плюс 48 часов до вердикта; вердикт около 27–44-х суток. Ступень A гейта — около 2.5 недель, ступень B — около 4–6.5 недель, а не 2 (Requirement 15.8, правка роадмапа в задаче 23). Откат сторожем запаздывает на 48 часов относительно последнего кластера точки.

## Автономность и автопродвижение

Платформа должна работать без обязательных действий владельца (решение владельца 2). Режим `promotion.mode`: `"auto"` в поставке (решение владельца 6); первое продвижение кодом невозможно до реализации сторожа (условие свежего сторожа и аренда), поэтому аварийные средства задач 16–17 появляются раньше; режим кодом не меняется, аварийно его меняет только владелец командой `./tb learn promotion`. Прогрев — условие, которое проверяет код при каждом проходе (`versions.promotion_ready`): среди последних 10 засчитываемых суток не меньше 7 полных проходов; за последние 7 × 24 часа работы сервиса цикла нет `CHAIN_BROKEN`, `DB_CORRUPT`, `WATCH_STALE`; сторож успешно отработал не позднее 3 часов назад; нет серии из 3 `STEP_ERROR` шагов наблюдения, вердикта и сторожа за 24 часа; последняя резервная копия не старше 24 часов и прошла `integrity_check`; `integrity_check` базы без ошибок. Прогрев проверяет живость цикла и целостность хранения; это не канареечный запуск правила на реальных входах. Если условия не выполнены 21 сутки, статус `WARMUP_STUCK`.

Учёт суток: засчитываются сутки UTC, когда сервис цикла работал ≥ 12 часов; полный проход — все суточные шаги выполнены или пропущены с кодом и `observe` успешен в ≥ 90% часов работы. Сутки с работой < 12 часов (платформа выключена владельцем) не засчитываются ни в плюс, ни в минус.

Ожидание продвижения ведётся на уровне правила (`rule_rows.wait`): испытание закрывается вердиктом и освобождает место в `max_parallel`. Причины ожидания: `READY` (условия готовности) — без срока; `MAX_ACTIVE` (лимит 10 активных правил) — без срока, видно на странице; `LOSS_CAP` (прогнозная доля прогонов, отсекаемых текущим набором вместе с новым правилом, по выборке окна 7 суток ≥ 0.4) — не дольше `loss_cap_wait_days` (14) суток подряд, затем правило и урок `rejected` (`LOSS_CAP`) без чёрного списка. `LOSS_CAP` использует ту же меру, что `TRADE_STARVATION` сторожа, поэтому продвижение само не вызывает отключения.

Два ожидающих правила продвигаются за один проход, только если не пересекаются по строкам (доля хитов одного, отсекаемых другим, в окне 7 суток ≤ 0.5); иначе продвигается правило с большим модулем среднего, а второе закрывается `NO_VERDICT` (`OVERLAP`) без чёрного списка.

## Надзор за надзором и аварийные средства

- **Единое правило безопасности.** `knowledge.rulebook_view` применяет активные правила только когда база читается и не восстанавливается (нет `runtime/knowledge.restoring`), аренда сторожа свежа (≤ `lease_h` = 6 часов) и `apply=true`; иначе режим без применения: торговля по базовому поведению мозга. Безнадзорное правило может молча блокировать торговлю, а отсутствие правила возвращает систему к состоянию без самообучения.
- **Простой платформы.** После старта платформы аренда может быть старой: правила не применяются до первой успешной проверки сторожа (≤ 1 часа), это не ошибка. `WATCH_STALE` (красный) — только если сервис цикла работает непрерывно дольше `lease_h`, а проверки сторожа за `lease_h` нет.
- **Сбой базы и восстановление.** Единственный исполнитель — сервис цикла. Повреждение в записях меток и шагах цикла распознаёт новый классификатор `knowledge.store2.is_corruption(e)`: только `sqlite3.DatabaseError` с основным кодом `sqlite_errorcode & 0xFF` = `SQLITE_CORRUPT`/`SQLITE_NOTADB` (без атрибута, Python < 3.11, — текст `malformed`/`not a database`), с проверкой цепочки `__context__`/`__cause__` (`SchemaMigrationError` оборачивает исходную ошибку, `labels/store.py:65-70`), и провал суточного `integrity_check`. Сервис меток, получив `DbCorruptError` в `label_step`, `capture_step` или в `open_rw` при старте, пишет сигнал `runtime/knowledge.corrupt` (pid, время, код); цикл проверяет его в каждом проходе `observe` (15 минут) и запускает протокол, сигнал снимается после успешного восстановления — повреждение, замеченное только сервисом меток, восстанавливается за один проход `observe`. Маркер восстановления сервис меток проверяет в `label_step` (на каждой метке), `capture_step`, `checkpoint_step` и `heartbeat`. `./tb labels backup` (`labels/cli.py:338` → `store.backup`) при маркере v2 переводится на `make_backup`, при маркере восстановления отказывает. `labels.store._is_corrupt` (строка 73) для этого не годится: для любой не-`OperationalError` он возвращает `True`, то есть нарушение `UNIQUE` в `trials` или срабатывание триггера append-only (`IntegrityError`) и закрытое соединение (`ProgrammingError`) запустили бы восстановление базы. Функция R1 не меняется (безопаснее для R1: её поведение в `open_rw` без маркера v2 прежнее); `database is locked` тоже не повреждение. На Windows открытый файл нельзя переименовать, поэтому правило соединений такое: все читатели, кроме долгоживущих писателей, открывают соединение на один вызов и закрывают его, а `labels.store.open_ro`/`open_rw` перед открытием проверяют маркер `runtime/knowledge.restoring` и при нём не открывают (известные читатели: `learn/vs_policy.py:72`, `labels/query.py:49`, `labels/cli.py` строки 166, 211, 267, 304, 325, операции дашборда, `./tb status`, `rulebook_view` в мозге и шлюзе — тоже на вызов, кеш в памяти держит только данные версии). Долгоживущие писатели кроме самого цикла — сервис меток (`labels/service.py:88` держит `self.conn`) и команды `./tb labels backfill|rerun` (`labels/cli.py:304`, `325`, `open_rw` на всё время работы). Каждый регистрируется файлом `runtime/knowledge.writers/<pid>`, при маркере не запускается, проверяет маркер перед каждой меткой (сервис меток — внутри `label_step`, проход которого до `LABEL_BUDGET_S` = 45 с, поэтому проверка на каждой строке пачки, а не раз за проход) и, увидев его, закрывает соединение (CLI прерывается) и пишет `runtime/knowledge.restoring.ack/<pid>`. Протокол: маркер → подтверждения → цикл закрывает своё соединение и ждёт подтверждений всех зарегистрированных живых писателей не дольше `restore_ack_timeout_s` (60 с, больше разметки одной метки) → выбор свежей проверенной копии → переименование повреждённого файла вместе с `-wal` и `-shm` (не удаляя) → проверка, что `-wal`/`-shm` у целевого пути отсутствуют → подстановка копии; переименование и подстановка с повторами и паузой при `PermissionError` (как `labels.store.backup`, `labels/store.py`, строки 173–183: до `BACKUP_TRIES` попыток с паузой 0.5 × номер) → запись `meta.copy_ts`, `meta.restore_ts` (исполнитель открывает соединение внутренним путём `store2` в обход проверки маркера) → снятие маркера → `AUTO_RESTORED`. Таймаут подтверждения, исчерпание повторов или оставшиеся `-wal`/`-shm` — протокол прерывается, маркер снимается, красный статус, ручной `restore`. затем шаг сверки статусов приводит уроки меток к восстановленной базе. При старте сервис цикла, найдя оставшийся маркер, проверяет файл и завершает или повторяет протокол. Если цикл не запущен — красный статус и ручной `./tb knowledge restore` (тот же протокол). Допущение: версии rulebook и записи чёрного списка новее копии теряются; копия после каждой смены версии и каждой записи владельца в чёрный список ограничивает потерю.
- **Чёрный список условий** — единственный механизм запрета повторной проверки. Ключ запрета — семейство условия `block_h = sha256("block:" + canon(семейство) + dir)`, 16 hex: числовые признаки без порога `(feature, op)`, категориальные со значением `(feature, op, value)`, элементы отсортированы; сдвиг квантиля меню не возвращает запрещённое условие, `coin_class = meme` в запрете не блокирует `coin_class = major`. Точный `cond_h = sha256(canon(cond) + dir)` — идентичность правила (тело правила); `DUP_ACTIVE` сравнивает и `cond_h`, и `block_h`; проверка (меню, приём и holdout кандидата, `rules.derive`, регистрация испытания) учитывает `block_h` и прежние записи по точному `cond_h`; колонка `blocklist_rows.cond_h` хранит ключ записи. `OWNER_DISABLE` и `OWNER_REJECT` — бессрочно до `./tb rulebook unblock <block_h>`; коды кода — фиксированные 14 суток (таблица ниже, колонка «Чёрный список»).
- **Аварийные средства (необязательные, вне пакета `tb.learnloop`).** Ровно три пути: `./tb rulebook disable <rule_id>` и кнопка `rule_disable` (одно правило); `./tb rulebook disable-all` (сначала `runtime/rules_switch.json apply=false`, действует всегда; затем версия `OWNER_DISABLE` без правил и чёрный список; при недоступной базе команда сообщает, что запись версии не сделана и её надо повторить после восстановления, отложенных файлов нет); `./tb rulebook apply on|off`. Плюс `./tb rulebook unblock`, `./tb learn promotion auto|off`, отклонение урока. Все пишут `OWNER`.
- **Сторож против нуля, испытание против базы.** Испытание требует, чтобы отсечённая часть была хуже базы (парный тест) и в среднем не лучше −`min_effect_r`; сторож откатывает, если отсечённая часть значимо лучше нуля на `rollback_delta_r`. Мёртвая зона принята явно: правило, у которого после продвижения отсечённая часть имеет среднее от −0.1R до +0.1R (или выше без значимости), остаётся активным. Чувствительность: точка 200 — около +0.18R, точка 50 — около +0.36R, недельная проверка (z ≈ 3.09) — около +0.26R; при 0.001 за год (52 проверки) вероятность ложного отката около 0.05.
- **Потеря входов.** Только по выборке окна `cluster_runs`: доля прогонов `P2` в области применимости, отсечённых активным набором, среди заполненных прогонов окна 7 суток (`b` — последняя граница часа с `cut_ts ≤ now`) выше 0.4 при ≥ 30 кластерах — отключение правила с наибольшим числом отсечённых прогонов (`TRADE_STARVATION`). Допущение: мера — прогоны `P2` в области применимости, а не входы мозга.
- **Смена версии.** Сторож считает только снимки версии политики и `ctx_ver` продвижения; при смене — точки заново, правило активно. Окно поиска меню при смене `ctx_ver` начинается заново (до 7 суток данных и 48 часов закрытия `NO_MENU`); holdout и открытое испытание при смене `ctx_ver` — `CTX_CHANGED` без чёрного списка; испытание при отключённой записанной версии политики — `inconclusive`.

Ступень A гейта этапа считает вмешательством только записи `OWNER` по объектам цикла (уроки меток, правила, команды `./tb rulebook` и `./tb learn promotion`).

В этих списках нет `chg_24h_pct` и `turn_24h_musd`, хотя строки сканера `marketdata/hotscan.py` их содержат. Без них `chg_24h_pct` на стороне мозга всегда `None`, а `coin_class` монет вне справочника — `unknown`, тогда как на метках (после пересчёта по `ev`) — `alt_mid`/`alt_small`/`meme`: паритет нарушен. Задача 33 добавляет оба поля в `D_FIELDS` (вид `num`) и в оба `NUM_KEYS`; это правка констант внутри `tb.core` и `tb.platform`/`tb.executor` без новых импортов, правила `tests/test_layering.py` (core не импортирует venues/executor) не затрагиваются. До этого и для событий без оборота `rule_features` возвращает `coin_class=None` (а не `unknown`), если монеты нет в справочнике `config/memory.json:coin_class`; правило по `coin_class` тогда не срабатывает и попадает в `feat_missing_ids`.

`memory.features.rule_features(event, cand, cfg) -> {признак: значение|None}` — единый источник; тест паритета прогоняет одну строку сканера по реальному пути мозга (`Publisher.convert` и `ScanBridge.convert` → `bus.sanitize` → журнал шины → `resolve_event` → `rule_features`) и по пути меток (`ev` сигнала → `rule_features`) и сверяет значения, включая случай `struct.sp` ≠ `d.spread_bps`; синтетический словарь события в обход шины для паритета не используется. Исключены из правил `range_15m_pct` и `btc_ret_1h_pct`. Исправление `labels/features.py:163` (задача 32) нужно для согласованности `feat` меток; цикл от него не зависит.

Доверие к `event_seq`: его присылает модель `chat` в аргументах `submit_plan`, поэтому в `h_submit` для `chat` он не используется — всегда берётся последнее событие монеты; `event_seq` задания раннера `entry_scout` (его ставит код раннера) принимается, только если это `scanner_signal` той же монеты, вида из области применимости и не старше `event_max_age_s`, иначе тоже последнее событие монеты. Так модель не может подставить событие чужой монеты, старое событие или `idea_stale` без рыночных полей. Чтение журнала шины: хвост текущего `events.jsonl` и предыдущий ротированный файл только если ротация была меньше `event_max_age_s` назад (ротация по суткам и по `MAX_FILE_BYTES`, `core/bus.py:439-457`), фильтр по `ts` и `sym`, старые файлы не сканируются.

Разрешение события: `rulebook_view.resolve_event(root, sym, event_seq, now, kinds)` — событие `event_seq` (задания раннера или вызова `submit_plan`); иначе последнее событие `scanner_signal` монеты из журнала шины с `d.kind` из видов области применимости (`range_5m`, `turnover_surge`, `hot_enter`, `oi_spike`, `liq_cascade`; не `idea_stale`/`idea_level`, `brain/brief.py`, строки 1416–1417) не старше `event_max_age_s` (900); иначе `None`. Обе точки вызывают одну функцию с одним источником, поэтому одно решение даёт одинаковый результат.

Рассмотрен вариант брать «последнее событие монеты» из таблицы меток `signals` (индексы `ix_sig_sym(sym, t0)` и `ix_sig_type(type, t0)`, `labels/schema.py:35-36`; поля `ev` — те же, по которым считаются признаки меток, то есть точный паритет). Отклонён: сервис меток захватывает `hot_events.jsonl` не чаще раза в `capture_every_s` = 15 с (`labels/service.py:129`), а захват и разметка идут в одном цикле, и проход `label_step` может занимать до `LABEL_BUDGET_S` = 45 с (строка 23) — задержка появления строки до ~60 с. Мозг будится событием `scanner_signal` сразу и строит досье через секунды, поэтому строки в `signals` чаще всего ещё не будет, и путь отката на шину стал бы основным: два источника вместо одного без выигрыша. Паритет обеспечивает задача 33 (поля `chg_24h_pct`, `turn_24h_musd` в шине) и тест паритета через реальный путь шины.

Записи `rule_eval`: шлюз по-прежнему дописывает их в `state/decisions.jsonl` (у базы знаний нет нового писателя, шлюз не открывает её на запись); шаг цикла `rule_eval_import` на каждом проходе переносит новые записи в `rule_evals`. Журнал решений ротируется: активный `state/decisions.jsonl` при `MAX_ACTIVE_BYTES` = 8 МБ под блокировкой переименовывается в `state/decisions.d/seg-<first_seq>.jsonl` (`core/decisions.py`, строки 95–100, 159–184), `seq` сквозной (строка 236), `manifest.json` хранит границы сегментов. Поэтому курсор `meta.rule_eval_cursor` — последний перенесённый `rec_seq`: чтение с сегмента, у которого `first_seq ≤ cursor + 1` (по именам `decisions.segments`, манифест лишь ускоряет), затем следующие сегменты и активный файл; `INSERT OR IGNORE` по (`rec_seq`, `rule_id`); оборванная последняя строка активного файла ждёт следующего прохода. Ротация между проходами записей не теряет: они уже в сегменте с `first_seq` после курсора. Записи — `kind="note"`, `what="rule_eval"` (`kind="rule"` засчитал бы `expstats.rules_by_plan`, `core/expstats.py:86`, как сработавшее правило плана). Таблица входит в копии и восстановление базы; после восстановления курсор из копии, перенос продолжается по `seq`. Подсчёты (`feat_missing_ids`, `RULES_NO_EVENT`, страница «Память», аудит) — SQL по `(ts, rule_id)` и `(ts)`. Без события правила не применяются, правила области попадают в `feat_missing_ids`; доля записей `rule_eval` без события за 7 суток выше 0.2 — жёлтый `RULES_NO_EVENT`.

Область применимости. Проверка правила идёт по политике `P2`: сигналы видов выше, сторона по направлению сигнала (`with_dir`), вход по подтверждению свечи, заполненные прогоны. Правило хранит `scope` и вне него не срабатывает.

## Словарь гипотез и эксперименты (Requirement 19)

Проверено по коду: тег гипотезы — `tags.hypothesis` плана (`core/plan_schema.py:210`, только шаблон `RE_TAG`), исполнитель кладёт его в сделку как `hyp` (`executor/core.py:922`); раннер по умолчанию пишет имя сетапа с подчёркиванием (`brain/entryplan.py:68`), `chat` — что угодно; `expstats._norm` берёт `hyp` как есть (строка 69), `group_stats` считает K по всем группам (ключ, режим) запроса (строки 294–310); `_b_experiments` (`brain/brief.py:252-272`) и `playbook.match`/`exp_index` (`brain/playbook.py:64-102`, +2 к рангу) работают на сырых ключах. Итог по данным: 20 ключей на ~70 сделках, K = 20.

- **Словарь.** `config/hypotheses.json`: `families` (14 `hyp` карточек `config/playbook.json` + `level-reject`, `momentum-chase` по сетапам `brain/validate.py:SETUPS` без своей карточки + `other`), `aliases` (имена сетапов и известные варианты), `policy_map`. Отдельный файл, потому что `config/experiments.json` имеет формат `{эксперимент: {...}}` и перебирается целиком (`expstats.load_meta`, `dash2/topics.py:1003`, `dash/model2.py:1122`). Модуль `tb.core.hyps` (чистый, читает только этот файл): `family(raw) -> (family, raw_or_None)` — нижний регистр, `_` → `-`, точное совпадение, `aliases`, самое длинное семейство-префикс с `-`, иначе `other`.
- **При подаче.** `h_submit` нормализует `tags.hypothesis`; неизвестное — `other` и `tags.hyp_raw` (новое необязательное поле `plan_schema`); план не отклоняется. Раннер подставляет семейство сетапа; описания инструментов перечисляют семейства.
- **При чтении.** `expstats._norm` вызывает `hyps.family` (`family(None)` → `None`; ключи `aliases` хранятся нормализованными), журнал не переписывается. Дашборд (`dash/model2.py`, около строки 1108, и `dash2/topics.py`, строки 987–1007) считает K сам по числу строк — переводится на общую функцию подтверждения `expstats` (задача 34). Подтверждение по `hyp`: K = число семейств, кроме `other`, с paper n ≥ 30 (не меньше 1), порог alpha / K. Пример: при трёх семействах с n ≥ 30 порог 0.0167 вместо 0.0025.
- **Справка меток.** `policy_map` по коду политик `config/shadow_policies.json` (`P2` `confirm_follow` — по направлению сигнала, вход по подтверждению; `P4` `fade_confirm` — против направления; `P5`, `P6` — базовые линии): `liq-cascade-reclaim` → `P4`/`liq_cascade`, `oi-flush-reclaim` → `P4`/`oi_flush`, `oi-build-squeeze` → `P2`/`oi_spike` — карточки с одним видом сигнала, чей вид и сторона совпадают с политикой. Многовидовые карточки (`range-fade`, `breakout-retest` и др.) однозначного соответствия не имеют и справки не получают. Шаг цикла `learnloop.hypref` раз в час считает по `policy_runs` за 14 суток (соединение на вызов, фильтр `env_norm`; это единственное явное исключение из правила «расчёты только по `cluster_runs`», Requirement 5.14, — справка решений не порождает) n кластеров (час, сторона), среднее значений кластеров, 95% t-интервал, `env_norm` и пишет `runtime/learn/hyp_ref.json`; `tb.learn` (только чтение, без записи на диск) и мозг (без импорта `tb.learnloop`) читают файл. Справка — ориентир, статус не меняет.
- **Досье.** `_b_experiments` возвращает строки по семействам с компактной справкой `ref: [n, mean, lo, hi]`; поле `win` из блока убирается, чтобы худший случай (`EXPERIMENTS_TOP` = 5 + 5 строк) не вырос по `brief.tokens`; `exp_index` получает семейства, `playbook.match` — прежнее +2.
- **Отклонение от принципа испытаний** записано: ранжирование карточек — контекст для модели, а не ограничение входа; статус пересчитывается на лету и снимается сам при ухудшении.

### Применение правил в мозге и шлюзе

Проверено по коду: кандидаты входа считает `brain/cands.py:candidates(brief, sym, ctx=None, root=None)`, которую вызывает только `brief.build` (`brain/brief.py`, строка 1426, `cands_mod.candidates(b, job_sym)` — сейчас без `root`, передача `root` добавляется, чтобы тесты не читали боевой каталог). `brief.build` используют раннер (`brain/runner.py`, строки 588–591) и шлюз (`gateway/catalog.py:h_brief`, строка 307 — так досье получает `chat`; `h_revise_idea`, строка 474). План входа оба пути подают операцией шлюза `submit_plan` → `gateway/catalog.py:h_submit` (строка 661; раннер — `brain/runner.py`, строка 1136). Ранние отказы `h_submit`: `plan_cli.precheck` и возврат `rejected_local` (строки 673–677), `check_scope` (678), `_need_trading` (679), `check_plan` (680), лимит планов в час (681–683). Поэтому:

- `brain/cands.py:candidates` после `logic.geometry.candidates` вызывает `rulebook_view.resolve_event`, `memory.features.rule_features` и `learn_rules.apply(rulebook_view.active(root), ...)`; кандидат с `fail` остаётся в `brief.cands` с `ok=false` и кодом `RULE_<id>`; валидатор повторно проверяет код отказа (модель не может его снять).
- `gateway/catalog.py:h_submit` после ранних проверок (строки 673–683) и до `_send` вызывает те же `resolve_event`, `rule_features` по монете и стороне плана и `learn_rules.apply`; при срабатывании активного правила отклоняет план `E_RULE_<id>` (`denied`); на каждый вызов, дошедший до этой точки, пишет запись `decisions` `what="rule_eval"`. Ранние отказы в знаменатель `RULES_NO_EVENT` и доли `feat_missing_ids` не входят.
- Правила `trial` и правила в режиме без применения ничего не отсекают и в первой итерации не записываются (`shadow_hits` — Requirement 18.7). При пустом rulebook вывод `brief.cands` и ответы `h_submit` совпадают с R1 поле в поле; запись `rule_eval` добавляется.

Ограничение: задание `entry_scout`, у которого правила отсекли все кандидаты, завершается `NO_CANDIDATES` до вызова модели и `submit_plan` не вызывает; разметка видна в `brief.cands`, записи `rule_eval` нет. Потерю входов сторож считает по `cluster_runs`, поэтому это не влияет на решения цикла.

```sql
CREATE INDEX ix_cr_t0 ON cluster_runs(policy_id, ctx_ver, env_norm, t0);

  wait TEXT, wait_since_ts INTEGER, from_lesson TEXT NOT NULL, env_norm TEXT NOT NULL, rulebook_ver_in TEXT, rulebook_ver_out TEXT, reason_code TEXT,

  numbers TEXT, ts TEXT NOT NULL, prev TEXT, h TEXT NOT NULL);

  verdict TEXT, numbers TEXT, cut_ts INTEGER, closed_ts INTEGER);
CREATE TABLE blocklist_rows(seq INTEGER PRIMARY KEY, cond_h TEXT NOT NULL, code TEXT NOT NULL, until_ts INTEGER, actor TEXT NOT NULL, ts TEXT NOT NULL);
CREATE TABLE rule_evals(rec_seq INTEGER NOT NULL, rule_id TEXT NOT NULL, ts INTEGER NOT NULL, role TEXT, event_seq INTEGER, no_event INTEGER NOT NULL,
  hit INTEGER NOT NULL, evaluated INTEGER NOT NULL, missing INTEGER NOT NULL, rulebook_ver TEXT, plan TEXT, PRIMARY KEY(rec_seq, rule_id));

CREATE INDEX ix_re_ts_rule ON rule_evals(ts, rule_id);
CREATE INDEX ix_re_ts ON rule_evals(ts);
CREATE TABLE learn_events(seq INTEGER PRIMARY KEY, ts TEXT NOT NULL, step TEXT NOT NULL, code TEXT, actor TEXT NOT NULL, ref TEXT, body TEXT);
-- индекс ix_sig_type_side_t0 ON signals(type, side, t0) создаёт только вторая итерация (поиск по меткам), в v2a его нет
-- триггеры: cluster_runs, rule_evals, rule_rows, rulebook_versions, blocklist_rows, learn_events: BEFORE UPDATE/DELETE -> ABORT;
-- meta: knowledge_v2_ver, copy_ts, restore_ts, rule_eval_cursor (последний перенесённый rec_seq журнала решений); until_ts NULL = бессрочно (снимает владелец новой строкой);
-- trials: BEFORE UPDATE OF trial_id, rule_id, lesson_id, criterion, criterion_h, start_ts, deadline_ts, env_norm, policy_id, policy_ver, ctx_ver -> ABORT; BEFORE DELETE -> ABORT
```

`feats` — JSON значений `RULE_FEATURES` прогона; `cluster` — `"<hour>:<side>"`. `rule_rows.wait` — `READY`, `MAX_ACTIVE`, `LOSS_CAP` или `NULL`; `wait_since_ts` — начало текущего непрерывного ожидания по `LOSS_CAP`. ## Correctness Properties

1. **Только ужесточение.** Для любого кандидата, плана и набора правил разрешённые входы с правилами ⊆ без них; размерные виды не создаются и не применяются при `allow_size_rules=false`. **Validates: Requirements 8.1, 8.2, 8.5, 8.6**
2. **Неизменяемость.** UPDATE/DELETE в защищённых таблицах (включая `cluster_runs`) отклоняются, цепочка `rulebook_versions` обнаруживает правку, при разрыве запись отказывает (`CHAIN_BROKEN`). **Validates: Requirements 2.2, 2.3, 2.10**
3. **Сохранность базы.** При маркере v2 повреждение базы не приводит к созданию пустой базы; копии не затираются, ротация по 3 на причину, повреждённый источник не копируется; восстановление выполняет только сервис цикла по протоколу с маркером и только после подтверждений закрытия соединений от всех живых держателей (иначе таймаут 60 с и красный статус), повреждённый файл переименовывается вместе с `-wal`/`-shm`, копия не подставляется при оставшихся `-wal`/`-shm`, сервис меток на время протокола не пишет. **Validates: Requirements 2.4, 2.5, 2.7, 2.11**
4. **Совместимость фасада.** Прежние тесты `memory` проходят без правок; `refresh` и `create` по умолчанию ведут себя как раньше для уроков мозга; `refresh` не меняет уроки меток; бюджет `propose` не учитывает уроки меток; `expires_ts = null` читается как «без срока». **Validates: Requirements 5.6, 5.16, 6.2**
5. **Детерминизм и ложные находки одного меню.** Два запуска на тех же снимках дают тот же результат независимо от порядка строк; на 400 наборах без закономерности допустимо не более 5 созданных `hyp` (ожидаемая вероятность на набор не выше alpha × alpha / K_h ≈ 0.00083, около 0.33 на 400). **Validates: Requirements 5.3, 5.5, 5.9**
6. **Повторный скрининг.** На нулевых данных с фиксированным seed из 200 серий по 8 последовательных недельных прогонов меню не более 5 серий дают хотя бы один `hyp` (ожидаемо около 1.3). **Validates: Requirements 4.1, 4.6**
7. **Окна не пересекаются.** Окна поиска, holdout и испытания строго последовательны; holdout начинается в момент приёма и длится ровно `holdout_days`, тест в нём один; в испытание попадают только кластеры с `t0 >= start_ts`. **Validates: Requirements 5.3, 9.3**
8. **Поправка на множественность.** Порог скрининга alpha / K (K ≤ 17), holdout alpha / 3, испытания alpha / `max_parallel`, сторожа alpha_watch / 3 в точках и `alpha_watch_weekly` еженедельно. **Validates: Requirements 4.2, 5.3, 5.4, 9.2, 11.2**
9. **Кластеры и парный тест.** Ключ кластера не зависит от условия; каждый прогон входит ровно в одну группу своего кластера; n — число кластеров теста; общий сдвиг всех прогонов часа не меняет статистику парного теста; в меню первой итерации нет условий по `utc_session` и `side`, а условия шире 0.3 прогонов отсеяны `TOO_BROAD`. **Validates: Requirements 4.1, 5.5, 5.13**
10. **Воспроизводимость выборок.** Каждый закрытый кластер записан в `cluster_runs` ровно один раз; выборка окна с записанными `a`, `b`, `cut_ts` даёт тот же хеш при любом повторе после `cut_ts`, в том числе если кластер окна закрылся через 47 часов после своего часа; расчёт раньше `cut_ts` не выполняется; переразметка `policy_runs` после закрытия ничего не меняет; подмена строки в обход триггеров даёт `SAMPLE_CHANGED`; после любого восстановления из копии (автоматического или ручного) окна с записанным хешем и `copy_ts < cut_ts ≤ restore_ts` закрываются `RESTORED` без ошибки целостности и без чёрного списка, окна с `cut_ts > restore_ts` продолжаются. **Validates: Requirements 2.11, 5.9, 5.14, 5.17, 9.3**
11. **Критерий до испытания.** `criterion_h` совпадает с хешем `criterion` (включая активный набор); изменить критерий нельзя; вердикт зависит только от первых `n_target` кластеров теста по `(t0, key)` выборки окна и критерия. **Validates: Requirements 9.2, 9.7**
12. **Словарь вместо текста.** Принятый кандидат не содержит значений вне словаря, claim содержит `effect` в 0..10 и проходит `validate_claim`; строка урока не превышает 4096 байт. **Validates: Requirements 4.4, 5.6, 16.1, 16.3**
13. **Уникальность идентификаторов уроков.** Параллельные `create` (цикл и `from_hint`, потоки и процессы) дают разные `lesson_id`. **Validates: Requirement 5.7**
14. **Идемпотентность шагов.** Повторный запуск шага на тех же данных не создаёт строк, версий и переходов статуса. **Validates: Requirements 11.7, 15.2**
15. **Граница полномочий.** Цикл не меняет `config/risk_profile.json`, `risk_levels.json`, `exec_limits.json`, `config/local/*` и не импортирует торговые слои. **Validates: Requirements 8.4, 8.7, 8.8**
16. **Откат восстанавливает поведение.** Множество разрешённых входов после отката равно множеству версии до продвижения. **Validates: Requirements 11.3, 11.4**
17. **Страница не врёт.** Числа блоков R2.6 равны пересчёту прямыми запросами; n < 30 помечено; вердикт «до/после» следует правилу Requirement 14.2. **Validates: Requirements 13.5, 14.1, 14.2**
18. **Сверка статусов уроков меток.** Любое изменение статуса урока меток создано `lessons.transition` из шага сверки или команды владельца; `tick.sync_now` и `refresh` уроки меток не меняют; любое терминальное состояние правила (`active`, `disabled`, `rejected` с любым кодом) выводит урок из `hyp`; после падения между записью версии rulebook и переходом урока следующая сверка переводит урок в `confirmed`; после восстановления базы из копии урок не идёт назад, а база приводится к нему (`RECONCILE_MISMATCH`); `conf_eff` урока меток не затухает. **Validates: Requirements 6.1, 6.2, 6.3, 6.6, 6.9**
19. **Независимость правила от урока.** Истечение, слияние или отклонение урока владельцем не меняют статус активного правила; отклонение владельцем закрывает открытое испытание и не активное правило и пишет `OWNER_REJECT`. **Validates: Requirements 5.12, 6.4**
20. **Атомарность и уникальность.** На один `rule_id` не более одной строки `trials`; правило и испытание создаются в одной транзакции или не создаются. **Validates: Requirement 7.9**
21. **Паритет признаков и общие точки.** Для одной строки сканера значения `RULE_FEATURES` по реальному пути мозга (`convert` публикатора → `bus.sanitize` → `resolve_event`) и по пути меток совпадают (с точностью округления, включая `chg_24h_pct`, `coin_class` по обороту и `spread_bps` из события); монета вне справочника без оборота даёт `coin_class=None` и `feat_missing_ids`; одно решение (монета, сторона, событие) даёт одинаковый результат в `cands.candidates` и `h_submit`; `resolve_event` не берёт `idea_stale`/`idea_level` и события старше 900 с; без события правило не срабатывает; запись `rule_eval` есть для каждого `submit_plan`, прошедшего ранние проверки, и только для них. **Validates: Requirements 7.7, 7.10, 7.11**
22. **Нет безнадзорных правил.** При просрочке аренды больше `lease_h`, недоступной или восстанавливаемой базе или `apply=false` `rulebook_view` не применяет правила; `apply=false` действует независимо от состояния базы; `WATCH_STALE` не возникает, пока цикл работает меньше `lease_h` после старта. **Validates: Requirements 2.6, 7.12, 7.15, 7.16, 11.9**
23. **Чёрный список — единственный запрет повтора.** Условие из чёрного списка не попадает в меню, урок и испытание до истечения срока или снятия владельцем; `LOSS_CAP`, `NO_VERDICT` по `OVERLAP`, `CTX_CHANGED` в чёрный список не пишут. **Validates: Requirements 4.5, 5.8, 5.15, 7.14, 9.9, 10.3**
24. **Пересечение по строкам.** Продвижение правила на другом признаке, отсекающего не больше 0.5 прогонов-хитов испытания, не закрывает испытание; при доле выше 0.5 испытание закрывается `NO_VERDICT` (`OVERLAP`); `lessons.overlap` для правил не вызывается. **Validates: Requirements 9.9, 10.5**
25. **Предельная потеря входов и `LOSS_CAP`.** Эффект и потеря входов нового правила считаются только по прогонам, которые не отсёк активный набор критерия; продвижение не выполняется, если прогнозная доля отсечённых прогонов набора с новым правилом ≥ 0.4, поэтому сразу после продвижения `TRADE_STARVATION` по тем же данным не срабатывает; ожидание по `LOSS_CAP` дольше 14 суток отклоняет правило без чёрного списка. **Validates: Requirements 9.3, 10.1, 10.3, 10.7, 11.6**
26. **Ожидание на уровне правила.** Испытание освобождает место в `max_parallel` в момент вердикта; ожидание по готовности и по лимиту активных правил не ограничено сроком. **Validates: Requirements 9.5, 10.3**
27. **Учёт суток.** Сутки с работой цикла < 12 часов не меняют счётчики прогрева и гейта; сутки ≥ 12 часов с `observe` < 90% часов — не полный проход. **Validates: Requirements 10.6, 15.6, 15.8**
28. **Автономность.** На фейковых часах и синтетике с закономерностью цикл без записей `OWNER` проходит путь меню → `hyp` → испытание → продвижение → откат. **Validates: Requirement 15.7**
29. **Окно испытания и смена версии контекста.** Без набора `n_target` в окне `[start_ts, deadline_ts)` решение `inconclusive` не принимается раньше `deadline_ts + cluster_close_max_h + observe_s` и учитывает поздно закрытые кластеры окна; смена `ctx_ver` во время испытания сразу закрывает его `CTX_CHANGED` без записи в чёрный список. **Validates: Requirements 9.6, 9.8**
30. **Семейства гипотез.** Для любого тега `hyps.family` возвращает значение из `HYP_FAMILIES`; варианты написания одной гипотезы (регистр, `-`/`_`, суффиксы через `-`, имена сетапов) дают одно семейство; неизвестный тег — `other` с `hyp_raw`, план не отклоняется; история сделок сводится к семействам без переписывания журнала. **Validates: Requirements 19.1, 19.2, 19.3**
31. **K по семействам.** K подтверждения гипотез равно числу семейств, кроме `other`, с paper n ≥ 30 (не меньше 1); `other` не подтверждается; для прочих разрезов `group_stats` K прежний. **Validates: Requirement 19.4**
32. **Справка не меняет статус и бюджет.** Справка меток есть только у семейств из `policy_map`, не меняет `confirmed` и ранг карточек; худший случай блока `experiments` по токенам не больше прежнего. **Validates: Requirements 19.5, 19.7, 19.8**

## Error Handling

| Ситуация | Поведение |
|---|---|
| Таблиц цикла нет | цикл не стартует (`NOT_READY`), `diagnose` и CLI работают, страница показывает заглушку |
| `KnowledgeMigrationError` | сервис меток работает, цикл в красном статусе |
| Повреждение базы при маркере v2 (`DB_CORRUPT`) | запись меток и цикла остановлена, правила в режиме без применения, красный статус, автовосстановление сервисом цикла (`AUTO_RESTORED`); цикл не запущен — ручной `knowledge restore` |
| Рядом с целевым путём остались `-wal`/`-shm` | подстановка копии не выполняется, красный статус |
| Маркер `knowledge.restoring` остался после сбоя | сервис цикла при старте завершает или повторяет протокол |
| `CHAIN_BROKEN` | запись в таблицу отказана, красный статус, торговля работает |
| Модель (вторая итерация) недоступна | `llm=false`, кодовый источник |
| Исключение в шаге | `STEP_ERROR` в `learn_events`, следующий шаг |
| Расчёт по окну раньше `cut_ts` | не выполняется, шаг ждёт следующего прохода |
| Меньше `discovery_days_min` данных, смена `ctx_ver` | `NO_MENU`; holdout и испытание в процессе — `CTX_CHANGED` без чёрного списка |
| Не все держатели соединения подтвердили закрытие за 60 с | протокол восстановления прерван, маркер снят, красный статус, ручной `restore` |
| Окно с `cut_ts` позже автоматически восстановленной копии | `RESTORED`, без ошибки целостности и чёрного списка |
| Не день меню | `NOT_DUE` |
| Условие шире 0.3 прогонов | `TOO_BROAD`, не в меню |
| Правило ослабило бы поведение или вышло за границы | `BOUNDS_BLOCKED`, версия без правила |
| Платформа только что запущена | правила в режиме без применения до первой проверки сторожа, без статуса ошибки |
| Цикл работает дольше `lease_h`, сторож не отработал | `WATCH_STALE`, правила в режиме без применения |
| Серия `STEP_ERROR` / исчерпаны рестарты сервиса | продвижение приостановлено (`promotion_ready`), аренда истекает, правила в режиме без применения |
| Прогноз потери входов ≥ 0.4 | правило ждёт (`LOSS_CAP`); дольше 14 суток — `rejected` (`LOSS_CAP`) без чёрного списка |
| Лимит активных правил | правило ждёт (`MAX_ACTIVE`) без срока |
| Продвинуто правило, пересекающееся по строкам > 0.5 | открытое испытание `NO_VERDICT` (`OVERLAP`), без чёрного списка |
| Падение между записью версии и переходом урока | следующая сверка статусов переводит урок |
| После восстановления базы урок «впереди» базы | сверка приводит базу к уроку, `RECONCILE_MISMATCH` |
| Хеш выборки изменился | `SAMPLE_CHANGED`, ошибка целостности |
| Нет события у решения | правило не срабатывает, `feat_missing_ids`; доля > 0.2 — `RULES_NO_EVENT` |
| Потеря входов выше порога | `TRADE_STARVATION` |
| `n_target` недостижим | `UNREACHABLE_N` |
| `disable-all` при недоступной базе | выключатель записан, команда сообщает о необходимости повторить запись версии |
| Более `events_per_day` строк | `EVENTS_THROTTLED` |

Ошибки цикла в шину как `error` не идут (будит мозга); агрегаты в heartbeat и `./tb status`.

## Порядок реализации (волны)

Нумерация волн совпадает с `tasks.md`.

Первая итерация: 0 — внешние события (слияние R1, утверждение спеки); 1 — диагноз, таблицы и защита базы, поля шины для признаков правил (`chg_24h_pct`, `turn_24h_musd`), конфиг и события, чистый модуль условий, исправление ключа оборота меток, словарь гипотез и нормализация при чтении (`core/hyps.py`, `expstats`); 2 — уроки меток в `memory.lessons`, повторный замер и мощность, единая функция признаков правил; 3 — снимки и выборки окна, меню и проверка, правила, версии и `rulebook_view` (с разрешением события); 4 — каркас цикла; 5 — применение правил в мозге и шлюзе; 6 — испытание, нормализация гипотезы при подаче; 7 — продвижение и сверка статусов; 8 — сторож, аварийные команды и отклонение урока владельцем; 9 — операции дашборда, блоки страницы; 10 — вкладка «Память», гейт, справка меток и блок гипотез (бэкенд); 11 — виджеты страницы (после вкладки «Память»: общий `frontend/dist`), слои и сквозные тесты; 12 — документация и приёмка первой итерации.

Вторая итерация: 13 — перенос случаев и уроков, поиск по меткам; 14 — переключение боевых данных, порт заданий и роли; 15 — ретроспектива, размерные правила, справочные уроки, заморозка, условие по нарушениям, `shadow_hits`, меню по сессиям; 16 — документация второй итерации.

Каждая волна откатывается флагом (`enabled`, `promotion.mode`, `allow_size_rules`, `store`). Реализацию ведут субагенты; главный агент проверяет дифф, тесты и границы полномочий.
